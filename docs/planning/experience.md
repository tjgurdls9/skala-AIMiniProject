# 첫 테마: 개발팀 사무실

상태: 화면 설계. 구현·브라우저 성능 검증 전. R19–R22를 구체화한다. 실행 필드와 상태는 [프로토콜](protocol.v1.schema.json), 승인 의미는 [계약](contracts.md)을 따른다.

## 1. 화면이 답해야 하는 다섯 가지

1. 원래 어떤 제품을 만들기로 했고 지금 적용되는 명세는 무엇인가?
2. 어느 Phase·Sprint에 있으며 누가 무엇을 실제 수행 중인가?
3. 무엇이 끝났고 어떤 근거로 통과·반려됐는가?
4. 내가 결정할 것은 무엇이며 승인하면 어떤 부작용이 생기는가?
5. 결과를 수정·중지·재개하거나 코드를 확인하려면 어디로 가야 하는가?

Signal_room의 역할별 캐릭터·근거 패킷·회의 구역·상세 패널을 차용한다. 원본의 고정 4인 좌석을 그대로 늘리지 않고, 여러 작업을 층위별로 탐색한다. 큰 규모는 모든 캐릭터를 한 방에 쏟아붓는 방식으로 표현하지 않는다.

## 2. 시각적 방향

**업무를 읽을 수 있는 작은 개발 스튜디오**를 지향한다. 첫 테마는 사용자가 부하를 고려해 선택한 사무실이다. 다른 테마보다 실제로 가볍다는 측정 결과는 아직 없다.

- 장면은 가벼운 2D Canvas, 조작과 정보는 DOM. 대형 3D 엔진·물리 시뮬레이션부터 도입하지 않는다.
- 배경은 따뜻한 회백색/짙은 잉크색, 사무실은 낮은 채도의 녹회색, 결정과 위험은 분명한 대비로 구분한다.
- 역할은 이름·아이콘·색을 함께 쓴다. 계획은 청색, 구현은 청록, 검증은 보라, 보안은 황토색 계열을 후보로 검토한다. 위험도 색과 역할 색을 혼동시키지 않는다.
- 본문·폼은 읽기 크기 16px를 출발점으로 하고 로그는 밀도 조절을 제공한다. 시스템 한국어 글꼴을 우선 사용해 외부 폰트 연결을 필수로 만들지 않는다.
- 일관된 간격·글자 위계·분할선으로 밀도를 관리한다. 모든 정보를 같은 카드나 과도한 네온 효과로 포장하지 않는다.
- 화면의 대표 요소는 **명세 회의실 → 구현 책상 → 서로 분리된 검토실 → 출시 게이트**로 이어지는 작업 전달이다.

위 색·수치는 디자인 제안이며 접근성 확인 뒤 조정한다. light/dark는 표시 옵션, office는 시각화 테마다. 두 개념을 같은 선택기로 섞지 않는다.

## 3. 데스크톱 정보 구조

```text
┌ 프로젝트 / LIVE·REPLAY / 무료 공급자 상태 / 명세 버전 / 중지 ┐
├ Phase 경로 ───── 현재 Sprint 목표 ───── 필수 AC 충족 현황 ───┤
│ 프로젝트 트리 │ 현재 Sprint 사무실 장면 │ 선택한 작업·근거   │
│ Phase         │ 회의실 / 구현 구역     │ 입력 명세·AC       │
│  Sprint       │ 검증실 / 보안실        │ 변경 diff·실행 결과│
│   작업        │ 출시 게이트            │ 보고서·출처·오류   │
├ 시간순 사건 기록 / 오류·승인 대기 고정 영역 ─────────────────┤
│ 프리뷰 열기 / 수정 요청 / 기획 승인 또는 배포 승인          │
└─────────────────────────────────────────────────────────────┘
```

프로젝트 → Phase → Sprint → 작업 → 아티팩트의 탐색 상태를 유지한다. 전체 지도에서는 Sprint 단위로 집계하고, 선택한 Sprint만 장면에 펼친다. 큰 로그는 페이지/구간 단위로 읽고 필터를 유지한다. 재연결·작업 추가 때문에 선택·스크롤·폼 입력을 초기화하지 않는다.

진행률은 “완료 작업 수/현재 계획 작업 수”와 “충족 AC/전체 AC”를 구분한다. 재계획으로 분모가 늘면 이유를 표시한다. 추론 시간이나 캐릭터 이동 거리로 퍼센트를 만들지 않는다. 완료 예상 시간은 실측 전 제공하지 않는다.

## 4. 장면과 실제 상태 연결

| 실제 사건 | 장면 표현 | 함께 표시할 근거 |
|---|---|---|
| 기획 초안 생성 | 회의실 문서 도착 | 명세·범위·미정 사항 |
| 승인 대기 | 회의실/출시 게이트 대기 배지 | 승인 대상과 변경 영향 |
| 구현 작업 시작 | 담당 좌석 활성화 | 작업 ID·분야·시작 시점 |
| 도구 실행 결과 | 근거 패킷 전달 | 도구·결과 요약·아티팩트 링크 |
| 검증·보안 진행 | 서로 구분된 검토실 | 같은 후보 커밋, 각자 진행 상태 |
| 검사 실패 | 해당 구역의 텍스트 오류 표지 | 실패 AC/검사·재현·수정 작업 |
| 추론/무료 한도 대기 | 좌석 대기 표지 | 대기 이유, 가능하면 제공사 재개 시각 |
| 사용자 중지 | 장면 정지·중지 처리 상태 | 취소 불가 외부 작업이 남았는지 |
| 배포 완료 | 출시 게이트 결과 도착 | 환경·커밋·digest·상태 확인 결과 |

걷기·문서 전달은 이미 수신한 공개 사건의 연출이다. 아직 발생하지 않은 성공을 먼저 연기하지 않는다. 유휴 동작은 유휴라고 표시하며 실제 작업으로 카운트하지 않는다. 검증실과 보안실을 분리해 그리는 것 자체는 백엔드 격리의 증거가 아니다. 접근 정책과 보고서가 별도로 필요하다.

장면 모션은 브라우저에서 처리한다. 모델을 프레임마다 부르지 않는다. 화면이 숨겨지면 렌더링을 줄이고, 사건이 없거나 모션 감소 설정이면 정적 장면을 쓴다. 고해상도 화면의 Canvas 픽셀 수와 표시 대상 수는 프로파일링 후 조정한다. 장면이 느려도 목록·승인·중지는 동작해야 한다.

## 5. 핵심 사용 흐름

### 최초 요청

빈 사무실에 요청 입력과 실행 가능성 표시를 제공한다. 로컬 모델·실행기·Git/배포 대상은 연결 여부와 자격 확인 상태를 구분한다. 키 존재를 API 인증·무료 자격으로 표시하지 않는다. 새 LIVE와 실제 기록 REPLAY를 명시 선택한다.

아이디에이션에서는 문제·사용자·제약을 정리하고 실현 가능한 소수 대안과 트레이드오프를 제시한다. 정보가 부족하면 가정을 표시한다. 최신 시장조사가 필수인 것처럼 유료 검색을 요구하지 않는다. 선택한 대안은 명세와 AC로 이어진다.

### 기획 승인

한 화면에서 목표·기능·비범위·AC·스택·저장소/브랜치·배포 대상·무료 모델 정책을 읽을 수 있어야 한다. 원문과 달라진 부분을 펼쳐 확인한다. `이 기획으로 구현 시작`과 `수정 요청`을 구분한다. 미정인 외부 작업 대상이 있다면 해당 부작용은 허용하지 않는다.

### 구현 중

현재 작업·대기 이유·최근 아티팩트가 먼저 보인다. 선택한 작업의 AC·입력 명세·관련 검색 근거·diff·실행 로그를 펼친다. 작업 완료와 Sprint 수용 완료를 구분한다. 사용자 수정 입력은 즉시 원장에 저장하고 영향 작업을 오래된 것으로 표시한다.

### 독립 검토·프리뷰

검증·보안 원본 보고서를 따로 열 수 있다. 한쪽 통과를 전체 합격으로 합치지 않는다. 프리뷰는 격리한 미리보기 주소와 커밋을 함께 표시한다. 외부 생성 앱은 별도 origin 또는 제한 iframe으로 열고 부모 앱 토큰·스토리지·secret에 접근시키지 않는다. 프리뷰 자체도 외부 공개/배포라면 허용된 테스트 환경인지 먼저 확인한다.

`이 부분 수정`은 아티팩트와 피드백을 연결한다. 기존 범위의 수정은 구현 Sprint, 기능·스택·데이터·배포 대상 변경은 기획 재승인으로 간다. 마음에 들지 않는 결과를 배포 승인 거절로만 표현하게 만들지 않는다.

### 배포 승인

배포 환경·노출 범위·커밋·이미지 digest·두 보고서·변경 요약·복구 대상을 보여준다. `이 결과를 이 환경에 배포`처럼 대상을 분명히 표시한다. 최신 대상이 바뀌면 이전 승인 버튼은 무효화하고 재검토를 요청한다. 중복 클릭·뒤로 가기·브라우저 재접속으로 중복 배포가 생기면 안 된다.

### 중지·재개

상단에서 항상 중지할 수 있다. 중지 처리 중에는 새 작업이 생기지 않으며 아직 결과 불명인 외부 작업을 표시한다. 재개 전 최신 명세·공급자 자격·후보·승인을 다시 확인한다. 중지와 실행을 취소하고 기록만 남기는 행동을 구분한다.

## 6. Jev 아이디어: 보조 정보 강조

사용자가 말한 아침판을 확인하면 `feed-curator`는 로컬 E5 임베딩으로 기사 관련도를 계산한 참고 구현이다. 공식 Jev의 공개 로컬 가중치나 동등 기능은 확인하지 못했다. 공식 API가 무료라는 확인도 없으므로 필수 의존성으로 채택하지 않는다.

첫 기능은 관심 축(예: 프론트·배포·보안)을 기준으로 관련 사건을 묶고, 상세 패널에서 읽을 자료를 추천하는 것이다. 우선 서버가 가진 작업 태그와 의존 관계를 사용하고, 로컬 Qwen 임베딩 검색이 준비되면 의미 관련도를 보완한다. 이를 Jev 모델을 실행했다고 표시하지 않고 `로컬 관련도 보조`로 표시한다.

| 보조 판단에 허용 | 허용하지 않음 |
|---|---|
| 관련 자료 추천·중복 사건 묶기·사용자 관심 작업 강조 | 배포 승인·보안 통과·AC 충족 판정 |
| 기본 정렬 안에서 추천 배지·읽기 순서 제안 | 실패·승인 대기 숨기기·읽을 수 없게 흐리기 |
| 명시 관심 변경 시 관련도 재계산 | 버튼 아래 갑자기 카드 재정렬·승인 대상 교체 |

실패·보안 차단·무료 소진·승인 대기는 점수와 무관하게 고정 노출한다. 추천이 실패하면 일반 시간순/업무순 탐색이 유지된다. 외부 Jev는 무료 조건과 데이터 정책이 확인된 경우에만 교체 가능한 후속 공급자로 검토한다. 모델 선택 제한을 확대 해석하지 않는다.

## 7. 반응형·접근성·상태

- 데스크톱 1440, 노트북 1024, 모바일 390px를 설계 확인 목표로 잡는다. 작은 화면은 장면→현재 작업→승인/근거 순의 한 열로 전환한다. 정확한 breakpoint는 실제 콘텐츠로 정한다.
- Canvas와 동등한 DOM 작업 목록·이름·상태를 제공한다. 모든 핵심 조작은 키보드로 가능해야 한다.
- 승인 dialog는 포커스 이동·가두기·Esc 닫기·복귀를 처리한다. 확인 없이 승인되는 키보드 지름길은 만들지 않는다.
- 모션 감소, 충분한 대비, 색 외 상태 표식, 읽을 수 있는 오류, 44px급 터치 표적을 목표로 한다. 빈번한 로그를 모두 screen reader live region으로 읽게 하지 않는다.
- 빈 상태·실행 중·오류·부분 결과·승인 대기·연결 끊김·무료 소진·모델 없음·REPLAY·성공을 별도로 디자인한다.
- 다크/라이트·목록/장면 전환은 실행·명세·선택 작업·승인 폼을 초기화하지 않는다.

## 8. 후속 테마 방향

| 테마 | Phase·Sprint 표현 | 승인·검토 표현 |
|---|---|---|
| 미래형 관제 | 구역·작업 셀·전달 궤적 | 관제 브리지 |
| 중세 길드 | 도시 구역·공방·의뢰 | 의회·검문소 |
| 오케스트라 | 악장·소절·파트 | 리허설·공연 승인 |
| 소설 | 부·장·장면·원고 | 편집 검토·출간 승인 |

같은 작업 ID·상태·승인·아티팩트에 시각 표현만 연결한다. `제2악장 · 구현 Phase`처럼 업무 용어를 병기한다. 첫 버전에는 사무실만 구현하고, 테마 변경이 런타임 상태를 바꾸지 않는 경계만 지킨다. 테마 수를 개발 능력의 지표로 사용하지 않는다.
