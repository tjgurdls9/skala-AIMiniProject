# 수용 시나리오

상태: **계획된 검증 기준, 미실행**. 시나리오를 적었다는 사실은 통과 증거가 아니다. 사용자가 승인한 생성 앱 자체의 AC는 각 프로젝트 명세에서 별도 관리한다. 아래는 자동화 제품의 기준이다.

P0는 첫 완주·출시 경계, P1은 첫 제품의 품질, Later는 후속 목표다. 구현 후 각 ID에 실행 버전·입력·아티팩트·실제 결과·미확인 한계를 연결한다. 현재 테스트를 추가하거나 실행하지 않는다.

## 2. 출시를 막는 보안 조건 초안

기획 승인에서 구체 검사와 적용 범위를 확정한다. 최소 후보는 비밀정보 검사, 정적 코드 검사, 의존성 취약점 검사, 이미지 검사, 실행 권한·경로·네트워크 경계 점검이다. 실제 선정 도구의 버전·룰·취약점 DB 시점을 기록한다.

- secret이 Git diff·로그·프론트 번들·모델 입력·공개 아티팩트에 포함됨.
- 허용 경로 밖 쓰기/읽기, 호스트 홈·Docker socket 접근, 미승인 외부 전송이 가능함.
- 재현 가능한 임의 코드/명령 실행·인증 우회·권한 상승·위험한 입력 처리가 확인됨.
- 적용되는 high/critical 의존성·이미지 취약점이 미해결이며 근거 있는 비적용 판정도 없음.
- 검사 도구가 실패·미실행·DB 불명인 상태를 PASS로 표시함.
- 후보 README/주석/검색 문서의 지시를 받아 검토를 생략하거나 보고서를 바꿈.

도구의 severity 숫자만으로 진실을 확정하지 않는다. 오탐·비적용은 증거를 갖춘 원본 보고서에 남긴다. LLM이 별다른 문제를 찾지 못했다는 이유로 결정론적 검사 오류를 상쇄하지 않는다. 보안 검사 결과는 알려진 문제에 대한 범위 내 평가이며 무취약성 보증이 아니다.

## 3. 추가 실패·복구 시나리오

| 상황 | 필요한 결과 |
|---|---|
| 승인 접수 직후 서버 종료 | 승인·작업 예약이 함께 존재하거나 둘 다 없음. 재접속 중복 부작용 없음 |
| Git push/deploy 응답 유실 | 외부 실제 결과 조회 후 조정. 확인 전 중복 실행·성공 선언 없음 |
| SSE 중복·누락·단절 | seq 중복 제거·재동기화. 실행 실패와 연결 실패 구분 |
| 원격 push가 자동 배포 트리거 | 배포 승인 전 push 금지 또는 비배포 브랜치 사용 |
| 검사 도구 업데이트 서버 접속 불가 | 최신 여부·실패 표시, 필수 검사 미완료로 출시 차단 |
| 프로세스 재시작 시 작업이 running | lease·원장·외부 상태 확인 후 복구. 과거 대화만 이어서 재실행하지 않음 |
| 디스크 부족·아티팩트 손상 | 저장 실패·무결성 불일치 표시. 원본 삭제·허위 성공 없음 |
| 악성 생성 앱 프리뷰 | 부모 앱 secret·토큰·스토리지 접근 불가. 필요한 외부 연결만 허용 |

## 4. 비교 실험은 후순위

초기에는 기능 확인과 복구 근거에 필요한 기록만 남긴다. 나중에 같은 모델·버전·양자화·자원·템플릿·요청으로 단일 에이전트/개선 버전을 비교할 수 있다. 완주율·AC 충족률·요구사항 누락·수정 횟수·사용자 개입·도구 오류·총 시간·최대 메모리를 후보 지표로 둔다. 이번 문서에는 성능 개선 수치를 만들지 않는다.
