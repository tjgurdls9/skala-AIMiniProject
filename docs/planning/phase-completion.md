독립 작업은 병행한다. Claude는 P01 계약 소비와 P02–P03의 확정된 상태 연결을 진행하고, Codex는 런타임을 진행한다. 시각 디자인 대기 중 Codex는 선행 입력이 있는 API·문서·배포 어댑터 준비를 진행할 수 있다. 사용자 디자인 수신을 대신 선언하거나 P04 완료/실제 배포로 진행하지 않는다.

사용자가 더 일찍 Claude에게 직접 디자인을 지시하면 원문을 보존하고 현재 데이터·기능 제약을 설명해 P04에 연결한다. 이미 충분한 직접 지시가 있으면 같은 내용을 다시 받기 위한 게이트를 만들지 않는다. 내용 변경이 실제 API/기능/데이터 범위를 바꾸면 Codex와 계약/명세 변경으로 분리한다.

Ollama 출력의 원본 스키마 검증과 단일 추론 슬롯을 유지한다.

**Claude:** 필요한 문맥 준비/대기 이유와 사용자 입력 요청을 확정된 공개 상태로 표시한다. 내부 사고 원문·모델 prompt 전체를 UI 로그로 노출하지 않는다.

**Claude:** 공개 근거의 출처·버전·실패를 근거 패널에 연결한다. 보조 관련도는 중요 사건을 숨기지 않게 유지하며 실제 미확인 Jev를 실행했다고 표시하지 않는다.

## 5. P03 — 개발·독립 검토 / S06–S07

**Codex**

**Codex:** 현재 같은 후보의 독립 validator/security와 불변 원본을 유지하며 분야별 결과에도 같은 규칙을 적용한다. 입력·파일·검색·메모리·도구와 공개 이벤트를 통한 상대 미확정 판정 유입을 차단한다. 구현자는 보호된 AC/정답을 수정하지 못한다. 도구 오류/not_run/fail을 출시 차단으로 남기고 새 후보/명세/검사 입력 회차의 재검사를 지원한다. 실제 scanner DB·도구/룰 버전과 범위를 보존하며 알려진 기준을 임의 완화하지 않는다.

**Claude:** 두 보고서의 명세·커밋·이미지 일치와 독립 판정을 보여준다. 한쪽 통과를 전체 통과로 표현하지 않는다. 원본/현재·옛 회차 구분과 실패 근거를 연결한다.

**P04 인계 묶음:** Codex는 실제 프로젝트/Phase/Sprint/작업·승인·AC·후보·보고서·프리뷰의 계약 버전과 대표 기록을 제공한다. Claude는 어떤 화면에 어떤 실제 데이터가 필요한지, 기존 화면에서 무엇이 연결됐고 남았는지 정리한다. 이를 바탕으로 다음 디자인 지시를 받는다.

## 6. P04 — 사용자 디자인 지시·사무실·수정 / S08–S09

### S08-A: 사용자가 Claude에게 직접 디자인을 지시하는 지점

**Claude의 필수 행동**
1. P03 인계를 확인하고 현재 화면의 구성·현재 URL/화면 자료(준비된 경우)·실제 데이터 연결 범위·남은 S08 UI 범위를 짧게 제시한다. 화면 자료가 없으면 없다고 밝히고 실제 구현 구조를 설명한다. 합성 화면은 합성이라고 표시한다.
2. 사용자에게 **지금부터 프론트 디자인을 직접 지시해 달라**고 요청한다. 별도 작성 양식을 요구하거나 관제탑이 디자인을 정하도록 넘기지 않는다. 사용자는 자연어·이미지·사이트·기존 화면 지적으로 지시할 수 있다.
3. `docs/handoffs/claude.md`에 `S08-DESIGN: 사용자 디자인 지시 대기`와 남은 작업을 남기고, 해당 디자인 구현은 실제 지시가 올 때까지 기다린다. 기다린 시간을 동의로 해석하지 않는다. 이는 개발용 인계이며 제품 API의 승인 이벤트로 합성하지 않는다.
4. 사용자의 직접 지시가 오면 원문/변경점을 기록하고 해당 범위를 구현한다. 이미 받은 충분한 지시가 있으면 그것을 연결한다. 모호함 중 구현에 필요한 부분만 질문한다. 요청하지 않은 별도 시안/승인 절차를 만들지 않는다.

이 단계의 직접 요청 문구와 전체 Phase 흐름은 [Claude 보완 프롬프트](../prompts/CLAUDE_PHASE_COMPLETION.md)에 포함한다. 독립 디자인 입력 템플릿을 전달하는 방식은 사용하지 않는다.

### S08-B: 지시된 디자인과 실제 상태를 함께 완성

**Claude:** 사용자가 지시한 화면 구성·사무실 표현·정보 밀도·상호작용을 현재 구조에서 구현한다. 프로젝트→Phase→Sprint→작업→아티팩트·AC·근거·오류/승인·중지/재개를 읽을 수 있게 한다. LIVE/실제 기록/예시 구분, 읽기 전용 재생, DOM/키보드/포커스·반응형·모션 감소·색 이외 표식을 유지한다. 요청 없는 추가 테마·3D·라이브러리 확대를 하지 않는다. 기능/계약 변경 요청은 Codex에게 전달하고 독립 가능한 디자인은 진행한다.

**Codex:** 필요한 공개 API/상태·출처·AC/보고서 계약을 제공하고 통합한다. 사용자 디자인 지시를 대신 작성하거나 frontend 소스를 고치지 않는다. 이 디자인 대기는 기존 생성 앱의 기획/배포 HITL과 별개다.

### S09: 실제 사용자 프리뷰·수정·재기획

검증 시작 전에 서비스 커밋·모델·도구·시작 환경·기준을 고정한다. 요청별 앱 코드는 내부 로컬 모델/도구 경로에서 생성한다. 작업 세션은 검증 앱을 직접 구현하지 않는다. 실패 후 서비스 수정은 별도 변경/새 실행으로 검증하며 중간 개입 기록을 보존한다.

**공동:** 실제 사용자 입력/기획 승인→검토 통과 후보 프리뷰→스타일 수정→새 후보/재검토·데이터 유지, 이어 기능/범위 변경→새 명세/기획 재승인 흐름을 연결한다. 사용자 입력이 필요한 시점은 그 사용자에게 실제로 요청하고 스크립트 승인을 대신 넣지 않는다. 이전 승인/판정 무효화, 오래된 프리뷰 표시, 입력 폼·선택·근거 보존과 중지/재개를 연결한다. 임시 서비스 교체/취소 후 정리와 데이터 보존을 구분한다. 명세 간 DB 호환이 불명확하면 자동 이전하지 않는다.

**통합/종료 근거:** 사용자 디자인 원문→구현 커밋·기준 API, 실제 사용자 기획/수정 기록·후보/검토/프리뷰의 연결을 인계한다. 사용자 디자인 지시 수신만으로 S08 완료, 스크립트 실행만으로 S09 실제 사용자 수용 완료를 선언하지 않는다.

## 7. P05 — 출시·복구·제출 / S10–S12

### S10: Git·배포 어댑터와 실제 배포 HITL

**Codex:** 기존 operation 원장과 후보 식별을 재사용해 저장소/push·배포 어댑터·환경 조회·복구 manifest를 구현한다. 원격 저장소·무료 대상/권한·push 자동 배포 효과·registry manifest digest·설정/데이터 호환을 확인한다. 실제 배포 전에 동일 명세/commit/image/env/두 보고서/복구 계획을 사용자가 검토·승인하게 한다. 승인 변경/중복/응답 유실은 실제 외부 상태 조회 후 조정한다. 대상·권한이 없으면 부작용 없는 구현/문서 준비를 진행하고 필요한 실제 입력만 요청한다. 승인 없이 push의 배포 효과를 발생시키거나 유료 자원을 만들지 않는다.

**Claude:** 실제 서버가 발급한 배포/복구 대상과 상태를 표시한다. 202 접수·진행·실제 결과·불명/실패를 구분하며 승인 해시를 만들거나 복구 성공을 연출하지 않는다. 디자인 지시와 일치하는 UI로 연결한다.

### S11: 전체 완주·복구·자원 근거

**공동:** 실제 사용자 승인·프리뷰 수정·Git·배포·복구의 전체 근거를 연결한다. 이전 단계에서 미확인인 재시작/인계·SSE 누락/중복·승인 직후 종료·외부 응답 유실·무료/자원 대기·긴 문맥/이력의 동작을 수용 시나리오에 대조한다. 실제 수행 범위·환경/버전·실패·미확인을 기록하고 범위가 제한된 자체/정적 검사와 실제 완주를 구분한다. 장비 메모리 경합을 기록하고 본인 확인용 프로세스만 정리한다.

### S12: 키 없는 별도 환경 열람·제출

**Codex:** 실제 원장/보고서/아티팩트의 비밀 제거·export/import·해시와 실행 버전을 연결한다. 키/모델 없이 읽는 재생과 Ollama LIVE의 설치 조건·lock·Compose/실행 안내·코드/보고서/배포 근거·라이선스를 제출 패키지로 정리한다. 모델 가중치·키·개인 데이터·대형 캐시는 제외한다. UI를 열었다는 이유로 생성 코드를 실행할 수 있다고 설명하지 않는다.

**Claude:** 키 없는 실제 재생의 탐색·근거·오류·읽기 전용·LIVE 조건 안내를 구현하고 프론트 사용법/현재 디자인 기준을 기록한다. 오래된 외부 URL을 현재 실행 중인 앱으로 표시하지 않는다.

**최종 종료선:** Codex가 S01–S12별 구현/근거/미실행·남은 문제·통합 커밋을 종합해 인계하고 양쪽은 배정 범위 종료 후 대기한다. 실제 배포/전체 수용이 불가능한 조건은 명시하고 완료로 덮지 않는다. 비교군·추가 테마·다중 사용자·임의 스택 확장을 끼워 넣지 않는다.

## 8. 공통 인계와 단계 전환

각 담당 인계에는 `현재 DEV-P/S·하위 작업 / 사용한 명세·계약/기준 커밋 / 변경 커밋·파일 / 완료 조건별 근거 / 실제 실행/미실행·실패 / 상대에게 필요한 입력 / 다음 실행 가능 작업·대기 이유`를 적는다. 상태 목록은 Codex가 소유하고 Claude는 자기 근거/요청을 기록한다.

한 Phase의 구현 인계 후 준비된 다음 작업을 이어갈 수 있지만, 전체 수용 조건이 없으면 그 Phase를 수용 완료로 표시하지 않는다. 선행 조건을 무시해 뒤 단계의 완료를 선언하지 않는다. 상대 완료 커밋을 읽고 통합하며 미완성 diff 복사·공유 계약 추측·상대 파일 수정·무한 폴링은 하지 않는다. 세션이 대기하면 다음 입력·누가 전달할지·이어갈 정확한 작업을 인계한다.

관제탑에는 문제/위험·확인된 Sprint/Phase 완료를 중심으로 보고한다. 사용자 디자인 지시 대기, 생성 앱 기획/배포 HITL, 권한/자원 부족은 실제 필요한 지점에서 사용자에게 알린다. 두 CLI를 자동 제어할 수 있다고 전제하지 않는다.
