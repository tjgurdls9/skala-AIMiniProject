# 구현·제출 계획

상태: 2026-10-20 개발 계획 정정. **이 제품 자체의 개발을 5개 Phase·12개 기준 Sprint로 관리한다.** 앞선 문서는 D0–D11 작업 묶음만 정하고 개발 Phase/Sprint를 확정하지 않은 누락이 있었다. 아래 구분은 이번에 보완한 계획이며 과거에 합의·수용됐던 것처럼 소급하지 않는다. 실제 작업 상태·변경·검사 근거는 담당 인계가 소유한다.

## 1. 첫 완주의 범위 제안

자동화 제품이 생성할 첫 앱은 **합성 CSV 기반 고객 문의 분류·처리 대시보드**로 제안한다. SKALA와 연결되는 데이터 처리·웹 구현·검증·보안·운영을 보여주면서 외부 비공개 데이터 없이 준비할 수 있다. 이 도메인은 아직 사용자 확정이 아니다.

생성 앱의 기획 승인용 AC 초안:

1. 고정 합성 CSV를 읽고 필수 열·자료형 오류를 명확히 반환한다. 실제 고객 개인정보를 입력하지 않는다.
2. 문의 목록·상세·분류/처리 상태 변경을 저장하고 새로고침 뒤에도 유지한다.
3. 분류별 집계가 실제 데이터·필터와 일치한다.
4. AI 기능을 선택하면 공유된 무료 모델 경로로 분류 제안을 만들고 실패/불확실성을 표시한다. 이를 검증되지 않은 자동 정답으로 저장하지 않는다. Data 처리만으로 시작할지 승인 때 결정한다.
5. 입력·API·화면·비밀·의존성 검사 근거와 Docker Compose 실행·health·배포/복구 절차를 제공한다.

도메인 분류 정확도 목표는 표본과 평가 기준 없이 임의 퍼센트를 약속하지 않는다. AI 정확도·속도와 전주기 자동화의 완주 성공은 따로 설명한다. 첫 앱을 CRUD로 줄여도 승인·독립 검토·수정·Git·배포 단계를 생략하지 않는다.

## 3. 개발 Phase·Sprint 기준

이 절은 **자동화 서비스를 만드는 Codex·Claude의 개발 계획**이다. 제품 런타임이 생성 앱에 부여하는 Phase/Sprint는 [아키텍처 §2](architecture.md)의 별도 데이터다. 아래 ID가 제품 DB·API 필드를 바꾸지는 않는다. 기존 D0–D11은 추적용으로 유지하고 개발 Sprint DEV-S01–S12와 일대일 연결한다.

12개는 첫 제출까지의 기준 Sprint 수다. 결함·요구 변경이 생기면 원 Sprint에 연결한 수정 작업 또는 추가 Sprint를 기록한다. 제품의 수정/재계획을 12회로 제한하거나 실패를 합격으로 바꾸는 상한이 아니다. 날짜·소요 시간·완료율은 근거 없이 붙이지 않는다.

어느 Phase도 현재 전체 종료 조건 충족으로 판정하지 않는다. 기존 기록의 생성 앱 `1 Phase·2 Sprint`는 제품 런타임의 데모 기록이며 이 개발 계획의 진척 수치로 사용하지 않는다. 근거의 자세한 범위는 [Codex 인계](../handoffs/codex.md)·[Claude 인계](../handoffs/claude.md)에 있다.

### 3.4 배정·종료·보고

- 배정에는 개발 Phase/Sprint ID·하위 작업·기준 커밋·소유 경로·선행 입력·산출물·완료 조건·이번 배정의 종료선을 적는다. 기존 D/F 작업은 하위 추적 ID로 유지한다.
- 한 Sprint 구현을 끝냈다는 보고에는 관련 AC·변경 커밋·실행한 근거·미실행/실패·남은 조건을 포함한다. 자체 검사 통과·합성 예시·실제 사용자 수용은 구분한다. 근거가 부족하면 부분 구현/수용 대기로 남긴다.
- 각 CLI는 **명시 배정된 Sprint 또는 Sprint 묶음의 종료선에서 인계하고 대기**한다. 다음 미배정 Sprint, 상대 소유 파일, 추가 에이전트, 외부 push/deploy로 범위를 자동 확대하지 않는다. 이미 배정된 복수 Sprint는 명시된 범위·의존성을 따른다. 매 Sprint마다 새로운 사용자 승인 게이트를 추가하는 규칙은 아니다.
- 관제탑은 문제/위험 또는 Sprint 수용 완료·Phase 종료가 확인됐을 때 알린다. 부분 시나리오 성공은 해당 범위를 붙여 보고하고 Sprint 전체 완료와 구분한다. 사용자 기획/배포 HITL은 기존 승인 규칙을 유지한다.
- **이번 보완 배정:** [P01–P05 보완 작업 지시서](phase-completion.md)의 남은 작업 전체를 양쪽에 나눠 전달한다. 각 Phase 인계 후 배정된 다음 준비 작업을 이어가며 P01만 끝내고 재개 지시를 요구하지 않는다. Claude는 P03 실제 데이터/계약 인계 뒤 P04/S08 본격 디자인 직전에 사용자에게 직접 디자인을 지시받는다. 그 입력·생성 앱 기획/배포 승인·상대 계약/산출물이 필요한 지점에는 대기 이유를 기록한다. 문서 수정만으로 CLI 전달·자동 재개·승인이 이루어지지 않는다.

담당별 전달문은 [Codex 보완 프롬프트](../prompts/CODEX_PHASE_COMPLETION.md)와 [Claude 보완 프롬프트](../prompts/CLAUDE_PHASE_COMPLETION.md)다. 작업자가 실제 수신·착수한 근거는 담당 인계/로그로 확인한다. Claude의 P04 직접 요청과 지시 대기는 후자의 프롬프트에 포함돼 있다. 사용자가 별도 디자인 입력 양식을 작성하는 방식은 사용하지 않는다.

라이브러리 버전은 착수 시 호환 버전을 lock한다. 테스트·수용 시나리오 실행은 사용자가 허용한 범위에서 수행한다. 이번 계획 정정에서는 제품 코드·계약·검사를 변경/실행하지 않았다.

**먼저 연결할 최소 세로 흐름:** 요청→명세→기획 승인→파일 생성 작업→독립 검토 결과→프리뷰→배포 승인→허용된 프리뷰 호스트. 캐릭터 디테일을 늘리기 전에 이 흐름과 실제 오류·중지·재개를 연결한다. 단, 접근성·권한 검증·비밀 차단은 후순위로 미루지 않는다.

## 4. 병행 가능한 작업과 순차 경계

D1 계약 이후 D7의 화면 골격을 준비할 수 있다. D5의 Front/Back은 API 계약·데이터 스키마가 고정된 뒤 각 공간에서 병행한다. D6의 검증·보안은 같은 통합 후보 생성 뒤 독립 실행한다. D9는 검토·사용자 프리뷰·실제 배포 대상이 준비되기 전 진행하지 않는다.

사용자가 연 Codex·Claude CLI가 [협업 프로토콜](collaboration.md)의 R&R에 따라 구현한다. 별도 ChatGPT 대화는 관제탑이며 두 CLI를 자동 기동·재개하지 않는다. agy는 이번 구현에 배정하지 않고, 추가 서브에이전트를 자동 기동하지 않는다. 제품 내부 멀티 에이전트 기능 구현은 이 개발 세션 운영과 구분한다.

## 6. 제출 패키지

- Git 저장소: 제품 코드·lock 파일·설정 예시·설계·생성 예제. 키·모델 가중치·개인 데이터·거대한 캐시는 제외한다.
- README: 키 없는 열람 → Ollama LIVE → 조건부 무료 API LIVE를 구분한다. 프론트만으로 코드 실행이 되지 않는다는 조건을 명시한다.
- 실제 실행 기록: 공개 이벤트·명세 버전·코드/검토/배포 아티팩트 해시·공급자/모델/런타임 버전·기록 시각. secret 제거 후 원본과 공개본의 관계를 설명한다.
- 결과 보고서: 문제 → 구현 포인트 → 실제 동작 근거 → 한계·트레이드오프 → 후속 개선. 비교 미실시를 명시하며 가짜 수치를 채우지 않는다.
- 발표: 요청 입력, 사무실 작업 분담, 독립 검사에서 반려, 수정 프리뷰, 승인된 배포와 재생 동선을 보여준다. 데모에서 실제 실패하면 실패·한계를 그대로 설명한다.

PDF의 기술 항목은 Multi-Agent·MCP·RAG·DI·LangSmith·모듈화·단위 테스트 등을 충분히 고려했는지 본다. 전부를 이름만 추가하는 것으로 점수를 보장하지 않는다. 이 설계는 역할 분담·MCP 3기능·기술 문서 RAG·주입 가능한 모델/도구·역할 모듈·검증 근거로 설명한다. LangSmith는 무료/보안 조건이 맞을 때의 선택 항목이다.

PDF의 Day3 13시·17시30분 일정은 과제 자료 기준이다. 현재 남은 실제 시간이 확인되지 않아 이 범위를 3일 안에 완성한다고 약속하지 않는다. 시간이 부족하면 추가 테마·범용 스택·보조 판단 고도화부터 미루고 전주기 핵심과 검토·승인 경계를 지킨다.
