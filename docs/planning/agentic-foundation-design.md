상태: **설계안(코드 없음).** 관제탑과 사용자가 확인하기 전에는 F1 이후 코드를 쓰지 않는다. 작성: Claude 런타임 세션, 2026-10-21. 기준 코드 `work/codex-runtime` `fdac850` 이후.
기준 문서: [requirements.md](requirements.md), [architecture.md](architecture.md), [delivery.md](delivery.md), [acceptance.md](acceptance.md), [phase-completion.md](phase-completion.md), [execution-boundary.md](execution-boundary.md). 근거 감사: [s09-intervention-audit.md](../reports/s09-intervention-audit.md).

## 0. 기준과 순서

1. 만드는 것은 **기획 문서에 이미 있는 workflow**다. 이 문서는 새 workflow를 만들지 않는다. "기획 단계 ↔ 현재 구현 ↔ 부족분"을 대조하고, 부족분을 메우는 도구·격리·기록의 설계만 더한다.
2. 그 workflow는 **Ollama 호출로 구현**된다. 앱 코드, 명령, 검증 기준의 내용은 앱 안의 에이전트가 만든다. 작업 세션이 만드는 것은 도구, 격리 실행 환경, 문맥, 독립 리뷰의 실행 틀, MITL 게이트, 기록이다. 신뢰 실행기는 정책 검사·격리 실행·기록만 하고 결과를 대신 만들지 않는다.
3. 순서는 **workflow 구축 → 구축 완료 판정(§6) → 시험 입력 투입(§7)** 이다. 카공지도를 포함한 어떤 요청도 구축이 끝나기 전에는 실행하지 않는다. 그전의 동작 확인은 단위·통합 테스트(가짜 모델)와, 필요할 때 관제에 먼저 알린 범용 소형 요청으로 한다.
4. 이 문서의 예시는 모두 일반 형태이며 특정 요청이나 기존 템플릿에서 출발하지 않는다. 기존 S09 DB와 run은 그대로 보존하고, 재개·worker 기동·Ollama 기동을 하지 않는다.

## 1. workflow 단계 ↔ 현재 구현 ↔ 부족분

시작 환경은 requirements §4가 정한 **FastAPI+Vue+SQLite+Docker Compose의 사전 고정된 빈 기반**이다. "빈"은 요청별 기능·예시·정답 코드가 없다는 뜻이다. 작업 세션이 데모를 채운 템플릿으로 대체하지 않는다(requirements §4, R30).

기준 흐름은 architecture §3의 다이어그램이다: 요청 → 아이디어 대안·명세·AC → 기획 HITL → 계약·Phase·Sprint·의존 작업 → 격리 구현 → 후보 커밋·이미지 → 독립 검증·보안 → 프리뷰 → (수정/재기획) → Git → 배포 HITL → 배포.

## 4. 부족분을 메우는 설계

### 4.1 작업 분해와 Supervisor (단계 2, R03·R07·R08)

- planner가 PlanDraft에 **작업 분해안**을 더한다: 작업 목록 `{id, 종류(infra|backend|frontend|ai|data|integration), AC 연결, 의존, 쓰기 범위(경로 패턴), 점검 연결}`과 **AI/Data 포함 판단과 이유**(포함하지 않으면 생략 이유). 사용자는 기획 승인에서 이를 본다(AC02).
- Supervisor는 **모델이 아닌 결정적 서비스 코드**다. 분해안을 검사한다: 순환 의존, 없는 작업 ID, 겹친 쓰기 소유권(architecture §2에서 "실행 전 오류"로 정한 항목), AC가 어느 작업에도 연결되지 않음. 실패하면 승인 대기로 가지 않고 planner에게 수정 근거와 함께 돌려준다. 반복 실패는 §4.9의 무진전 감지로 `needs_input`.
- 공유 계약(스키마·API 형태)이 필요한 분해는 계약 작업이 선행하고 그 산출물을 의존 작업이 읽게 한다. 두 작업이 같은 경로를 쓰려 하면 분해 검사에서 거절한다. 통합 작업이 최종 책임을 진다(AC08).
- Phase/Sprint: 기획 문서의 제안 구간(발견·기획 / 설계·기반 / 기능 구현 / 검증·보안 / 출시)을 상태 전이에 대응시킨다. Sprint는 날짜가 아니라 연결된 AC와 산출물(후보, 두 보고서)이 있을 때 닫는다. 검토 수정 Sprint는 기존 규칙(`store.py:286`)처럼 새 Sprint로 만든다.
- 병행 실행은 하지 않는다(슬롯 1). 의존이 없는 작업도 순차로 처리한다.

### 4.2 빈 시작 프로젝트와 모델 도구 (단계 4)

- 시작 상태("사전 고정된 빈 기반"): 빈 git 저장소와 서비스 소유의 환경 선언(`workspace.json`: 기본 스택 FastAPI+Vue+SQLite+Docker Compose, 포트, 데이터 경로, 자원 한도). 기본 런타임 이미지는 Python과 Node LTS 2종을 digest로 고정한다. 앱 코드·기능·테스트·예시는 없다. 의존성은 선언된 스택 범위에서 모델이 고른다. 시작 해시를 모든 기록에 남긴다.
- 모델이 직접 호출하는 도구(역할·단계별 허용 목록):

| 도구 | 동작 | 서비스 검사·기록 |
|---|---|---|
| `list_files`, `read_file` | 조회 | 작업 공간 내부, 크기 상한 |
| `write_file(path, content, expected_digest)` | 생성·수정 | `..`·절대·심볼릭 링크·`.git` 거부, 작업의 쓰기 범위 안인지 검사, 바이트·파일 수 상한, digest 충돌 |
| `delete_file`, `move_file` | 삭제·이동 | 같은 경로 정책, 삭제 전 digest 기록 |
| `run_command(argv, cwd, timeout)` | 격리 컨테이너 안 실행 | argv 배열만(셸 없음), 허용 실행 파일 목록, 시간·출력·프로세스 상한 |
| `install_dependencies(manager, packages)` | 설치·잠금 파일 | §4.2의 D1 경로, 정확한 버전·해시 기록 |
| `run_tests(selector)` | 테스트 | `run_command`와 같은 격리, 종료 코드·요약 기록 |
| `start_preview()` | 앱 기동 | 선언된 포트만, 프리뷰 프록시 경유, 외부 egress 없음 |

- 후보 고정(`freeze`)과 이미지 빌드는 서비스가 수행한다. 입력은 작업 공간 그대로다. 앱의 시작 명령·포트·상태 확인 경로는 builder가 선언 파일로 낸다.
- **모든 호출은 불변 도구 원장**(`역할, 작업, 도구, 인자, 종료 코드, stdout/stderr digest, 시각`)에 남는다. 원장에 없는 작업 공간 변경이 있으면 그 run은 개입 run으로 표시한다.
- 격리: 기존 한도(비권한, 읽기 전용 루트, capability 제거, 메모리 512m, CPU 1, 프로세스 64, `runner/sandbox.py:123`)를 유지한다. 작업 공간만 쓰기 가능하고 호스트 홈·Docker 소켓·키·환경변수는 주지 않는다. 기본 네트워크 none.
- 의존성 설치(D1 결정): 설치 단계에서만 공개 레지스트리 PyPI·npm으로 열리는 허용 목록 프록시. 무료 경로이며 요청·응답 요약이 도구 원장에 남는다. 그 밖의 네트워크는 차단한다. 승인된 계획의 "의존성 허용 범위"를 넘는 설치와 허용 밖 호스트 요청은 자동 허용하지 않고 `needs_input`.

### 4.3 요청별 검증 기준 (단계 1·6)

- planner는 AC마다 **선언형 점검 명세**(`check_spec`)를 제안한다. 코드가 아니라 데이터다. 종류: `http`(요청/기대 상태·JSON 일부), `command`(argv/기대 종료·출력), `file`(존재·내용 조건). 브라우저 점검은 v1 제외(D3).
- 스키마 검사로 거절한다. AC에 연결된 점검이 하나도 없으면 그 AC는 "자동 검증 없음"으로 표시되고 승인이 막힌다. 사용자가 계획을 고치거나 "사람이 확인함"으로 명시해야 승인할 수 있다.
- 점검 명세는 승인 대상 digest(`check_plan_digest`)에 묶인다. 승인 후 변경은 재기획이다.
- validator는 구현과 분리된 세션에서 고정된 후보 이미지로 **새 컨테이너**를 만들고 일반 `check_runner`로 승인된 점검을 실행한다. 판정은 기대값과 실제 결과의 기계적 대조다. 모델이 쓴 "통과" 문장은 근거가 아니다. validator 모델의 추가 점검은 별도 표시한다. 구현자가 쓴 테스트는 참고일 뿐 유일한 합격 근거가 될 수 없다(arch §6).
- AC는 연결된 점검이 모두 통과해야 `met`. 미실행은 `not_run`, 도구 오류는 `error`이며 통과가 아니다(기존 의미). 보안 역할은 같은 후보에서 별도 검사를 하고 두 보고서는 서로 보지 못한다.
- `validate.py`와 템플릿별 스크립트 선택은 `check_runner` 하나로 대체된다.

실제 모델 실행(`docs/reports/model-comparison-20261021.md`)에서 builder가 구현을 import하지 않는 자체 정의 테스트로 형식상 GREEN을 만든 사례가 나왔다. 그래서 두 가지를 추가로 고정했다: (1) `command` 점검은 승인 명세 안에서 **자기 완결인 인라인 코드**(`python -c`, `node -e`)만 허용하고 시험 실행기·builder 테스트 파일·스크립트 파일 실행은 계획 단계에서 거부한다(기획 승인 화면에서 사용자가 보는 점검이 곧 실행될 점검이다). (2) 후보 이미지에는 builder의 테스트 파일을 넣지 않는다(이력에는 남는다). 보안 역할은 모델 후보에서 표준 라이브러리 + 승인된 의존성의 import 이름(설치된 배포판 메타데이터로 해석, 해석 불가는 `unverified_import`) + 후보 내부 모듈만 허용한다.

### 4.4 ECC 흐름과 역할 (R12)

| ECC 단계 | 서비스 역할·세션 | 입력 | 권한 | 산출물 |
|---|---|---|---|---|
| 계획 | planner | 원문 조각, 승인 spec 또는 `prior_draft`, 검색 근거 | 계획 제안만 | PlanDraft, AC, 작업 분해, `check_spec` |
| TDD RED | builder(test 작업) | 해당 AC·점검 명세 | `write_file`, `run_tests` | 실패하는 테스트와 **실패 원장 기록** |
| TDD GREEN | builder(impl 작업) | 같은 AC, RED 기록 | 같은 도구 | 통과 기록 |
| 리팩터 | builder(선택) | 통과 기록 | 같은 도구 | 변경 후 통과 기록 |
| 독립 리뷰 | validator, security | 승인 명세·읽기 전용 후보 | 읽기 전용 + 격리 실행 | 불변 보고서 |
| 문맥 유지 | 서비스 문맥 계층 | 원문·승인 spec·체크포인트 | — | 역할별 패킷 |

- 서비스가 순서를 강제한다. impl 작업은 같은 AC의 test 작업이 실패를 원장에 남긴 뒤에만 열린다. 처음부터 통과하는 테스트는 RED 불성립으로 기록하고 사람에게 넘긴다.
- 역할은 같은 가중치를 써도 세션·메모리·도구·입력이 분리된다. code-reviewer 성격의 비차단 품질 보고서는 D4.

### 4.5 Git과 이력 (단계 5·8, R02)

- 작업 공간은 프로젝트별 영속 git 저장소다. 후보 고정은 작업 완료마다 서비스가 커밋한다(작성자 서비스, 메시지에 작업 ID와 도구 원장 참조). 후보 = 특정 커밋 + 이미지 digest. 두 검토와 프리뷰는 같은 커밋·이미지를 대상으로 한다(기존 규칙).
- 같은 프로젝트의 후속 run은 이전 이력 위에서 이어간다. 실패한 후보 커밋도 지우지 않는다.
- 원격 push는 배포 승인 이후다. 자동 배포를 유발하는 저장소라면 push 자체가 배포 부작용이므로 승인 전 수행하지 않는다(arch §3, 수용 시나리오 §3).

### 4.6 RAG (R23)

- 현재 코퍼스는 역할 문서 3개뿐이고 생성 앱의 스택 문서가 없다. 코퍼스에 채택 스택의 공식 문서와 허용 예제를 고정 버전·라이선스·해시와 함께 넣는다(arch §8). 요청별 정답이나 평가 정답은 인덱싱하지 않는다. 필수 요구사항은 검색에 맡기지 않고 직접 주입한다.
- 모델 역할이 `search_documents`를 호출하는 경로를 builder·validator·security에 허용한다(역할 ACL 유지). 검색 실패는 "근거 없음"으로 반환한다.

### 4.7 문맥 유지 (R11–R13)

- 유지: 원문 불변 저장, 명세 버전, 승인 무효화, 필수 조건 `mandatory()` 주입, 체크포인트, 역할별 패킷 분리.
- 변경 없음: 예산 상수와 정정 근거. 승인된 spec만 `approved_spec`, 미승인 직전 초안은 `prior_draft`.
- 추가(테스트로 고정): 일반 요청 유형별 문맥 동작(F0).

### 4.8 MITL (R04·R05·R06)

| 게이트 | 사용자가 보는 것 | 결속 대상 |
|---|---|---|
| 기획 승인 | 범위, AC, 작업 분해(AI/Data 판단·이유), 점검 명세, 허용 스택·의존성, 도구·명령 범위, 네트워크 정책, 외부 접근 요청, 무료 정책 | `spec_version_id`, `plan_digest`, `check_plan_digest`, `tool_policy_digest`, `contract_digests` |
| 수정·재기획 | 직전 초안과의 차이, 변경 요청 원문 | 이전 승인 무효화, `prior_draft`로 이어짐 |
| 구현 중 수정 | 후보·프리뷰 | spec이 같으면 새 구현 Sprint, 바뀌면 재기획 |
| 범위 밖 요청 | 승인 범위 밖 의존성·네트워크·외부 호출 | 자동 허용하지 않고 `needs_input` |
| 배포 승인 | 커밋·이미지 digest, 환경 설정 해시, 두 보고서, 복구 manifest | 기존 `ReleaseTarget` |

승인과 부작용은 분리한다. 외부 데이터 접근은 요청 내용이 아니라 **계획의 외부 접근 요청**(대상, 목적, 쿼터, 비밀 필요 여부)으로 표현하고, 승인된 범위만 브로커가 연다. 비밀은 모델·작업 공간·로그에 들어가지 않는다.

### 4.9 소형 모델·16GB 제약 (R14–R17·R25)

- 호출 단위: 한 AC, 한 파일(또는 한 명령 결과). 계획은 원문 조각, 구현은 AC×파일. 단위를 만들 수 없는 큰 요청은 원문을 보존한 채 `needs_input`으로 "범위를 나누라"고 요청한다.
- 자원: 추론은 슬롯 1 순차. 샌드박스 컨테이너·프리뷰·검증 컨테이너는 동시 수를 제한하고, 부족은 대기로 보인다.
- 상한 대신 **무진전 감지**: 연속한 시도가 같은 실패 증거 digest를 내면 반복하지 않고 증거와 함께 `needs_input`. 스키마 위반·도구 오류·자원 부족은 원인을 구분해 기록한다.
- 정답 보정 금지: 정답 코드, 요청별 힌트·예시, 기능이 든 scaffold를 넣지 않는다. 허용: 도구 호출 형식 설명, 일반 ECC 절차 지침, 언어·도구 중립 형식 예시. 못 하는 일은 그 결과가 측정값이다.

### 4.10 아이디어 대안 (단계 1, D7)

기획 문서 §3은 "요청 원문 → 아이디어 대안·명세·AC"로 시작한다. 최소 구현은 다음과 같다.

- planner가 명세 앞에 **대안 2–3개**를 낸다: `{id, 요약, 서로 다른 점, 위험}`. 호출은 1회 추가다(4B·슬롯 1 비용으로 허용).
- 사용자는 기획 승인 MITL에서 하나를 고르거나 수정을 요청한다. **선택된 대안 id가 명세에 결속**된다(`plan_digest` 안). 선택 없이는 승인할 수 없다. 대안이 하나뿐이어야 하는 사소한 요청은 planner가 대안 1개와 "대안이 하나뿐인 이유"를 낸다(대안 수를 억지로 채우지 않는다).
- 이후 명세·AC·작업 분해·점검 명세는 **선택된 대안**에서만 만든다. 수정·재기획에서는 이전 선택이 `prior_draft`에 남고 새 승인에서 다시 선택한다.
- 계약: `PlanDraft`/`PlanView`에 대안 목록과 선택 id가 추가된다. 프론트 표시가 필요하므로 계약 전용 커밋으로 먼저 알린다(D6와 동일 절차).

삭제는 사용자 결정이다. 근거는 감사 문서 §3·§4.

| 대상 | 제안 |
|---|---|
| 템플릿 ID 분기 8곳 이상(`pipeline.py:341`, `review.py:42`, `sandbox.py:87`, `release.py:72`, `contracts.py:46-48`, `config.py:25`, `api.py:130,135`, `infra/checks/preview.py:47-49`) | 시작 프로젝트 ID를 `workspace.json` 데이터로 읽고 이름 비교를 제거. `runner/`·`backend/`·`infra/`에 특정 템플릿·공급자 이름이 없음을 정적 테스트로 강제(프론트 `task-neutral`과 같은 방식) |
| 요청별 구현 파일(템플릿 앱 코드) | 실행 경로에서 분리해 "개발자 제공 참고 자료"로 격리하는 안. 삭제 여부는 사용자 결정(D5). 서비스 테스트의 가짜 모델 픽스처가 쓰고 있어 중립 픽스처가 먼저 필요 |
| 요청별 평가 스크립트(`validate.py`, `validate_cafemap.py`) | `check_runner`로 대체 후 격리 |
| `backend/map_access.py` | 범용 외부 접근 브로커로 일반화: 허용 공급자·경로는 코드가 아니라 승인된 계획의 외부 접근 요청에서 받는다. 비공개 키 파일, 일일 한도, 429 중단, 응답 상한은 유지 |
| 공급자별 검색 어댑터 | 서비스 경로에서 분리(모델이 만들어야 할 앱 로직) |
| `Runtime.reasons`, `plan_support` 문구 | 템플릿 이름이 아니라 계획에서 계산한 지원 공백(점검 없는 AC, 승인 범위 밖 의존성)만 서버가 만든다 |
| 계약 `template_id` enum | 시작 프로젝트 ID 패턴 문자열로 일반화(CR-C16)하되 서버 목록 검사도 같이 일반화(D6) |

## 6. "workflow 구축 완료" 판정 조건

아래를 모두 만족해야 구축 완료다. 하나라도 비면 시험 입력을 투입하지 않는다.

| 조건 | 판정 근거 |
|---|---|
| C1 §1 표의 부족분 1–7(아이디어 대안 포함)이 닫혔다(8·9는 승인 대상 생성까지) | 단계별 통합 테스트 목록과 결과 |
| C2 §8의 F0–F6 테스트가 RED→GREEN으로 모두 통과, 커버리지 80% 이상 | 테스트 출력, 커버리지 보고 |
| C3 특정 템플릿·공급자·시험 입력 이름이 `runner/`·`backend/`·`infra/`에 없다 | 정적 테스트 |
| C4 가짜 모델로 **범용 소형 요청** 하나가 §1의 단계 1–7을 끝까지 통과한다: 계획 → 기획 승인 → 작업 분해 → RED/GREEN → 두 독립 보고서(점검 명세 기반) → 프리뷰 → 로컬 커밋 → 배포 승인 대상 생성. 승인은 테스트 픽스처 사용자 조작이며 실제 사용자 승인으로 세지 않는다 | 통합 테스트와 원장 |
| C5 모델 호출 스모크: 범용 소형 요청 1건으로 도구 호출 형식과 원장 기록이 실제 `qwen3.5:4b`에서 동작함을 확인한다(품질 평가 아님). 실행 전에 관제에 알린다 | 원장, 실패 시 실패 기록 |
| C6 독립 코드 리뷰와 보안 리뷰에 CRITICAL/HIGH가 남지 않았다 | 리뷰 보고서 |
| C7 §3의 AC 충족 경로 표에 실제 증거(테스트·원장)가 연결되고 미확인이 명시됐다 | 갱신된 추적표 |
| C8 S09 DB와 run이 변경되지 않았다(구축 중 해시 동일), worker·Ollama 실행 이력이 시험 입력과 무관하다 | DB 해시 비교 |
| C9 **사람 확인 AC의 승인 경로(MITL)가 있다**: `manual_acceptance`로 표시된 AC(화면·사용성 등)를 사용자가 후보(커밋·이미지 digest)와 AC id에 결속해 확인·승인하고, 그 기록이 validator 판정과 별도로 남으며 validator의 `not_run`을 `met`으로 바꾸지 않는다. 이 경로 없이는 그런 AC를 가진 후보는 출시할 수 없다 | 통합 테스트와 승인 원장 |
| C10 관제탑과 사용자의 확인 | 사용자 확인 기록 |

## 7. 구축 완료 후 시험 (3단계 조건표 초안)

시험 입력(예: 카공지도)은 **workflow가 제대로 도는지와 품질이 어느 정도인지** 보려는 입력이다. 구축 완료(§6) 후에만 투입하고, 실행 도중에는 손대지 않는다.

| 항목 | 고정 값 |
|---|---|
| 서비스 커밋 | §6 완료 시점의 해시 |
| 추론 모델 | `qwen3.5:4b`(태그·digest), 슬롯 1 |
| 임베딩 | `qwen3-embedding:0.6b`(digest) |
| 도구 목록·정책 | §4.2 도구, `tool_policy_digest`, 허용 실행 파일, 네트워크 정책 |
| 빈 시작 상태 | 시작 작업 공간 해시와 `workspace.json` 해시 |
| 입력 요청 | 사용자가 앱에 입력한 원문 그대로(변형·보강 금지). 전송 주체 기록 |
| 외부 접근 | 계획 승인에서 사용자가 허용한 범위만. 키는 비공개 파일 |
| 개입 규칙 | 작업 공간·계획·점검·DB에 개발자 직접 수정 없음. 서비스 결함을 발견하면 run을 종료·보존하고 수정 후 새 run |
| 평가 기준(사전 등록) | 아래 |

평가는 "앱이 완성됐는가"가 아니라 **단계별로 모델이 무엇을 했고 어디서 막혔는가**를 기록한다. (1) AC와 점검 명세를 만들었는가, 점검 없는 AC 수 (2) 사용자 결정이 사용자 조작으로 기록됐는가(합성 승인 0건) (3) 모든 파일 변경이 원장에 있는가 (4) RED 뒤 GREEN 순서 (5) 두 보고서가 승인 점검으로 기계 판정됐는가(`not_run`·`error` 불통과) (6) 실패를 모델 판단 / 서비스 결함 / 환경 미준비로 분류 (7) 자율 수행 단계와 사람이 넘겨받은 단계를 구분. 비교 실험은 하지 않는다(R24).

## 8. TDD 계획

모든 항목은 가짜 모델로 서비스 동작을 검증하며, 요청 내용에 기대지 않는다. 각 항목은 RED를 먼저 확인한다. 순서는 F0 → F6이고 단계 끝마다 관제에 보고한다.

| 단계 | 테스트 |
|---|---|
| **F0 문맥 유형별** (착수 가능: 기존 문맥 장치의 범용 결함만, 모델·worker·Ollama 기동 없음, 예산 상수 불변) | 짧은 요청 1회 완료 / 긴 원문 다조각 완료 / 여러 차례 정정에서 폐기된 요구가 되살아나지 않음 / 재기획에서 `prior_draft` 전달·`approved_spec`은 승인본뿐 / 예산 초과 시 필수 조건을 자르지 않고 `needs_input`과 원문 보존 / 역할별 패킷에 다른 역할 보고서가 없음 / 동일 입력의 체크포인트 재사용 |
| F1 도구·격리 | 경로 이탈·심볼릭 링크·`.git`·크기 상한 거부 / 쓰기 범위 밖 거부 / 허용 밖 실행 파일 거부 / 셸 메타문자 미해석 / 네트워크 none / 시간·출력 상한 / 모든 호출이 원장에 남음 / 원장 불변 |
| F2 대안·작업 분해·점검 명세 | 대안 2–3개 또는 1개와 이유 / 선택 없이는 승인 불가 / 선택 id가 `plan_digest`에 결속 / 재기획 후 재선택 / 순환·없는 ID·겹친 쓰기 소유권 거절 / AC 미연결 거절 / AI/Data 생략 이유 필수 / 점검 스키마 위반 거절 / 점검 없는 AC는 승인 불가 / `check_runner`가 기대값과 실제를 대조 / 모델의 "통과" 문장은 판정에 무영향 / `not_run`·`error`는 통과 아님 |
| F3 RED→GREEN | RED 기록 없이 impl 작업이 열리지 않음 / 처음부터 통과하는 테스트는 RED 불성립 / 무진전 감지가 `needs_input`으로 이어짐 |
| F4c 독립 검증 | 승인된 점검이 후보 이미지에서 실행됨 / 점검 실패 시 AC unmet·후보 미통과 / builder GREEN이 AC 근거가 되지 않음 / command 점검은 인라인 코드만 / 이미지에 builder 테스트 없음 / 보안 모델 모드 |
| F4d 사람 확인 승인(C9) | `manual_acceptance` AC를 후보·AC id에 결속해 사용자가 승인 / 승인 없이는 출시 불가 / 판정 기록 분리 |
| F4 승인 결속·Git | `check_plan_digest`·`tool_policy_digest` 변경 시 이전 승인 무효 / 범위 밖 의존성·네트워크 자동 허용 없음 / 승인 합성 불가 / 작업별 커밋과 이력 보존 / push는 배포 승인 이전 불가 |
| F5 분기 제거 | 특정 템플릿·공급자 이름이 코드에 없음(정적) / 시작 프로젝트 ID는 데이터에서만 읽음 / 중립 픽스처로 서비스 테스트 이관 |
| F6 개입 감지·통합 | 원장 밖 작업 공간 변경이 있으면 개입 표시 / 가짜 모델의 범용 소형 요청 1–7단계 통합(C4) |

사용자가 "최선의 방향으로 결정해서 구현"을 위임했고 관제탑이 아래대로 결정했다(2026-10-21).

| ID | 결정 |
|---|---|
| D1 | 의존성 설치는 허용 목록 프록시. 대상은 공개 레지스트리 PyPI·npm뿐, 무료, 원장에 기록. 그 밖의 네트워크는 차단, 범위 밖 요청은 `needs_input` |

## 10. 이 설계가 보장하지 않는 것

- 4B 모델이 완성된 앱을 만든다는 보장은 없다. 못 만드는 경우의 올바른 결과는 막힌 단계의 기록이다.
- 격리 환경 안에서 모델이 만든 코드가 안전하다는 보장은 없다. 독립 보안 검사와 사람의 배포 승인이 남는다.
- 선언형 점검 명세가 모든 종류의 요구(시각적 품질, 사용성)를 표현하지는 못한다. 그런 AC는 "사람 확인" 표시와 함께 사용자에게 남는다.
- 이 문서는 구현 계획이다. 어느 단계도 이미 충족됐다고 주장하지 않는다.
