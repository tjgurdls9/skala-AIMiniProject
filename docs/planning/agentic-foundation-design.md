# 공통 기반 설계안: 빈 시작 프로젝트에서 로컬 모델이 아이디에이션부터 배포까지 수행하게 하기

상태: **설계안(코드 없음).** 관제탑과 사용자가 확인하기 전에는 구현하지 않는다. 작성: Claude 런타임 세션, 2026-10-21. 기준 코드 `work/codex-runtime` `ecc7259`.
관련: [architecture.md](architecture.md) §2·§4·§6·§7·§9, [execution-boundary.md](execution-boundary.md), [감사 문서](../reports/s09-intervention-audit.md).

## 0. 최상위 기준

모든 요청의 **구현과 실행은 앱 안의 Ollama 에이전트**가 한다. 작업 세션(Codex·Claude)이 만드는 것은 아래뿐이다.

| 서비스가 만든다 | 서비스가 만들지 않는다 |
|---|---|
| 에이전트가 쓸 도구, 격리 실행 환경 | 앱 코드, 시작 코드의 기능, 요청별 정답 |
| 역할별 문맥과 권한 분리 | 명령, 테스트, 검증 기준의 내용 |
| 독립 리뷰의 실행 틀 | 검토 판정을 대신 내리는 일 |
| MITL 게이트, 불변 기록 | 사용자 승인·결정의 합성 |

설계 기준 사례는 두지 않는다. 이 문서의 예시는 모두 일반 형태이며, 특정 검증 과제나 기존 템플릿에서 출발하지 않는다. 설계의 시험 대상은 §8의 일반 요청 유형이다.

신뢰 실행기의 역할은 **정책 검사, 격리 실행, 기록**이다. 결과를 대신 만들지 않는다. 명령의 종료 코드와 출력은 격리 환경이 낸 그대로 기록하고, 모델이 쓴 "통과했다"는 문장은 근거가 아니다.

## 1. 빈 시작 프로젝트에서 모델이 하는 일

### 1.1 시작 상태

- 빈 작업 공간: 내용이 없는 git 저장소 하나와 서비스가 소유한 실행 환경 선언(`workspace.json`: 허용 스택, 포트, 데이터 경로, 자원 한도). **앱 코드·기능·테스트·의존성 목록을 담지 않는다.**
- 시작 상태의 해시를 고정해 모든 실행 기록에 남긴다(§7). 요청에 따라 시작 상태가 달라지지 않는다.

### 1.2 모델이 직접 호출하는 도구 (builder 역할, MCP)

현재 도구는 `search_documents`, `read_file`, `patch_file`뿐이고(`runner/mcp_server.py`), 파일 4개 고정 경로에 대한 교체만 가능하다(`runner/access.py:13`). 아래로 대체·확장한다.

| 도구 | 동작 | 서비스의 검사·기록 |
|---|---|---|
| `list_files` | 작업 공간 트리 | 읽기 전용, 경로 정규화 |
| `read_file` | 파일 읽기 | 작업 공간 내부만, 크기 상한 |
| `write_file(path, content, expected_digest)` | 생성·수정 | `..`·절대 경로·심볼릭 링크·`.git` 거부, 파일·바이트 상한, 이전 digest 충돌 검사 |
| `delete_file`, `move_file` | 삭제·이동 | 같은 경로 정책, 삭제 전 digest 기록 |
| `run_command(argv, cwd, timeout)` | 격리 컨테이너 안에서 명령 실행 | argv 배열만(셸 해석 없음), 허용 실행 파일 목록, 시간·출력·프로세스 상한 |
| `install_dependencies(manager, packages)` | 의존성 설치와 잠금 파일 생성 | §1.4의 경로만 사용, 설치된 정확한 버전·해시 기록 |
| `run_tests(selector)` | 테스트 실행 | `run_command`와 같은 격리, 종료 코드·요약 기록 |
| `start_preview()` | 앱 기동(감독되는 장기 프로세스) | 선언된 포트만, 프리뷰 프록시 경유, 외부 egress 없음 |
| `freeze()` | 후보 고정 | 커밋·이미지 빌드는 서비스가 수행, 입력은 작업 공간 그대로 |

모든 호출은 불변 도구 원장에 `{role, task_id, tool, 인자, 종료 코드, stdout/stderr digest, 시작·종료 시각}`로 남는다. 원장은 "이 변경을 모델이 했다"는 유일한 근거다. 개발자가 작업 공간을 직접 고치면 원장에 없는 변경이 생기므로 그 실행은 개입 표시가 붙는다(§7).

### 1.3 격리

- 기존 한도를 유지한다: 비권한 사용자, 읽기 전용 루트, 모든 capability 제거, no-new-privileges, 메모리 512m, CPU 1, 프로세스 64, 로그 비활성(`runner/sandbox.py:123`).
- 작업 공간만 쓰기 가능한 마운트다. 호스트 홈·Docker 소켓·키·환경변수는 주지 않는다.
- 기본 네트워크는 none이다. 네트워크가 필요한 단계는 §1.4와 §4의 승인 경로만 쓴다.

### 1.4 의존성 설치 (결정 필요 D1)

설치에는 네트워크가 필요한데 격리와 충돌한다. 두 방식을 제안하고 선택을 사용자에게 맡긴다.

- (A) 오프라인 미러: 서비스가 패키지 저장소의 고정 버전 사본을 소유한다. 모델은 목록에서 고른다. 안전하지만 모델이 쓸 수 있는 라이브러리가 사전 정의된 범위로 줄어든다.
- (B) 허용 목록 프록시: 설치 단계에서만 패키지 저장소 도메인으로 향하는 프록시 경로를 연다. 설치 직후 닫는다. 정확한 버전·해시는 잠금 파일과 원장에 남는다. 라이브러리 선택은 모델이 하되, 승인된 계획의 "의존성 허용 범위"를 넘으면 `needs_input`이다.

권장은 (B)다. (A)는 라이브러리 목록을 서비스가 정하는 순간 "정답을 미리 채워 두는" 쪽으로 기운다. 어느 쪽이든 외부 모델 API와 유료 서비스는 금지한다(무료 정책 유지).

### 1.5 모델이 할 수 있는 범위와 서비스가 막는 범위

- 할 수 있다: 파일 생성·수정·삭제·이동, 승인된 범위 안의 의존성 설치, 빌드·테스트·실행, 실패 원인 읽기와 재시도.
- 막는다: 작업 공간 밖 접근, 허용 실행 파일 밖 명령, 승인 범위 밖 네트워크·의존성, 비밀 형식 출력, 다른 역할의 보고서 열람, 승인·배포.

## 2. 요청별 검증 기준

현재는 `infra/checks/validate.py`의 고정 점검 6개와 템플릿별 스크립트 선택(`runner/review.py:42`)이 검증을 정한다. 이를 **계획이 제안하고 사용자가 확인하는 선언형 점검**으로 대체한다.

### 2.1 계획 단계의 산출물

planner는 기존 `PlanDraft`에 더해 다음을 제안한다.

- AC: `{id, 설명, 관찰 가능한 조건}`
- 점검 명세(`check_spec`), AC에 연결된 목록. 코드가 아니라 **선언형 데이터**다.

```json
{"id":"C1","ac_ids":["AC1"],"kind":"http","steps":[{"request":{"method":"POST","path":"/x","json":{}},"expect":{"status":201,"json_subset":{}}}]}
{"id":"C2","ac_ids":["AC2"],"kind":"command","argv":["<tests>"],"expect":{"exit":0}}
```

종류는 `http`, `command`, `file`(존재·내용 조건)로 시작한다. 브라우저 점검은 v1에서 제외한다(D3).
- 근거: 모델이 쓴 검증 코드를 특권 환경에서 실행하지 않고, 고정 6개 대신 요청마다 달라지는 기준을 표현할 수 있다.
- 형식 검증: 스키마로 거절한다. AC에 연결된 점검이 하나도 없으면 그 AC는 "자동 검증 없음"으로 표시되며 `implementation_allowed`가 막힌다. 사용자가 계획을 수정하거나 "사람이 확인함"으로 명시적으로 표시해야 승인할 수 있다(합성 금지).

### 2.2 승인과 결속

사용자는 기획 승인 화면에서 AC와 점검 명세를 함께 본다. 승인 대상 digest에 `check_plan_digest`를 넣는다. 승인 후 점검 명세는 바꿀 수 없고, 바꾸려면 재기획이다.

### 2.3 독립 리뷰의 실행

validator 역할은 구현자와 분리된 세션·권한으로 실행한다.

1. 고정된 후보 이미지에서 새 컨테이너를 만든다(구현 작업 공간과 공유하지 않음).
2. 승인된 `check_spec`을 일반 실행기(`check_runner`)로 실행한다. 판정은 실행기가 선언된 `expect`와 실제 결과를 대조해 기계적으로 낸다.
3. validator 모델은 **추가 점검 명세를 제안**할 수 있다(적대적 시도, 경계값). 추가 점검은 validator 전용 공간에서만 만들고, 결과는 보고서에 "승인 외 추가 점검"으로 따로 표시한다. 구현자가 쓴 테스트는 참고용이고 유일한 합격 근거가 될 수 없다(architecture §6).
4. AC는 연결된 점검이 모두 통과해야 `met`이다. 점검이 실행되지 않으면 `not_run`, 도구 오류는 `error`이며 둘 다 통과가 아니다(기존 의미 유지).
5. 보안 역할은 같은 후보에서 별도 검사를 한다. 두 보고서는 서로 보지 못한다(기존 규칙 유지).

`validate.py`, `validate_cafemap.py`는 `check_runner` 하나로 대체되고, `infra/checks`에는 요청 내용을 아는 코드가 남지 않는다.

## 3. ECC 흐름과 역할 대응

| ECC 단계 | 서비스 역할 | 세션·입력 | 권한 | 산출물 |
|---|---|---|---|---|
| 계획(`planner`) | planner | 요청 원문 조각, 승인 spec 또는 `prior_draft`, 검색 근거. 구현 코드 없음 | 계획 제안만(승인·실행 불가) | PlanDraft, AC, `check_spec`, 작업 분해(§5) |
| TDD RED | builder(test 작업) | 해당 AC와 점검 명세, 작업 공간 | `write_file`·`run_tests` | 실패하는 테스트와 **실패 기록** |
| TDD GREEN | builder(impl 작업) | 같은 AC, RED의 실패 원장 | 같은 도구 | 통과하는 구현과 통과 기록 |
| 리팩터 | builder(선택 작업) | 통과 기록 | 같은 도구 | 변경 후 통과 기록 |
| 독립 리뷰 | validator, security | 승인 명세·읽기 전용 후보. 구현 대화·상대 보고서 없음 | 읽기 전용 + 격리 실행 | 불변 보고서 |
| 문맥 유지 | 서비스(문맥 계층) | 원문·승인 spec·체크포인트·미해결 실패 | 해당 없음 | 역할별 패킷, 체크포인트 |

- **서비스가 순서를 강제한다.** impl 작업은 같은 AC의 test 작업이 "실패하는 테스트"를 원장에 남긴 뒤에만 열린다. 테스트가 처음부터 통과하면 RED 불성립으로 기록하고 사람에게 넘긴다. 모델이 RED를 건너뛰어도 막는 것은 모델의 정직이 아니라 원장이다.
- ECC의 code-reviewer 성격(코드 품질 검토)은 validator·security와 다른 축이다. v1에서는 비차단 보고서로 둘지 사용자가 정한다(D4).
- 역할은 같은 가중치를 공유해도 세션·메모리·도구·입력이 분리된다(architecture §3).
- 현재 문맥 구현(`runner/context.py`)의 3층(원문 보존·권위·작업)은 유지한다. 미승인 직전 초안은 `prior_draft`로 따로 싣고 `approved_spec`과 섞지 않는다(`f9b074e`).

## 4. MITL 지점과 결속

| 게이트 | 사용자가 보는 것 | 결속 대상 |
|---|---|---|
| 기획 승인 | 범위, AC, 점검 명세, 허용 스택·의존성 범위, 허용 도구·명령 범위, 네트워크 정책, 외부 접근 요청, 무료 정책 | `spec_version_id`, `plan_digest`, `check_plan_digest`, `tool_policy_digest`, `contract_digests` |
| 수정·재기획 | 직전 초안과의 차이, 변경 요청 원문 | 이전 승인을 무효화(`invalidated`)하고 새 spec을 만든다. 직전 초안은 `prior_draft`로 이어진다 |
| 구현 중 수정 | 후보와 프리뷰 | 같은 승인 spec이면 구현 작업만 새로 만든다. spec이 바뀌면 재기획이다 |
| 범위 밖 요청 | 모델이 승인 범위 밖 의존성·네트워크·외부 호출이 필요하다고 보고 | 자동 허용하지 않고 `needs_input`으로 사용자에게 올린다 |
| 배포 승인 | 후보 커밋·이미지 digest, 대상 환경 설정 해시, 두 보고서, 복구 manifest | 기존 `ReleaseTarget`. 두 보고서가 같은 후보를 가리켜야 한다 |

- 승인과 부작용은 분리한다. 승인 없이 push·배포·외부 호출을 하지 않는다(architecture §4).
- 외부 데이터 접근은 요청 내용이 아니라 **계획에 명시된 외부 접근 요청**(대상 도메인, 목적, 쿼터, 비밀 필요 여부)으로 표현한다. 사용자가 계획 승인에서 허용한 범위만 브로커가 연다. 비밀은 모델·작업 공간·로그에 들어가지 않는다.

## 5. 현실 제약과 설계

제약: `qwen3.5:4b`(약 3.3GB), 추론 슬롯 1, 메모리 16GB, 문맥 예산 14000바이트(`runner/context.py:8`).

- **작업 단위**: 한 호출에서 모델이 다루는 것은 한 AC, 한 파일(또는 한 명령 결과)이다. 계획 단계는 이미 원문을 조각내어 호출한다(`fragments`). 구현도 AC×파일 단위로 쪼갠다. 단위를 못 만들 만큼 큰 요청은 `needs_input`으로 사용자에게 "범위를 나누라"고 요청한다(원문은 보존).
- **자원**: 추론은 슬롯 1이라 순차다. 샌드박스 컨테이너(512m)와 모델은 동시에 올라 있으므로 builder 샌드박스 1개, 프리뷰 1개, 검증 컨테이너 1개를 넘기지 않는 스케줄링을 서비스가 한다. 자원 부족은 대기로 보이게 한다.
- **실패 처리**: 총 횟수 상한은 두지 않는다(R25). 대신 **무진전 감지**를 둔다. 연속한 시도가 같은 실패 증거 digest를 내면 반복하지 않고 `needs_input`으로 증거와 함께 사람에게 넘긴다. 그 밖에 모델 출력의 스키마 위반, 도구 오류, 자원 부족은 각각 원인을 구분해 기록한다.
- **정답 보정 금지**: 작은 모델을 위해 정답 코드, 요청별 힌트 파일, 요청별 예시 출력, 기능이 담긴 scaffold를 넣지 않는다. 허용되는 것은 (a) 도구 호출 형식 설명, (b) 일반적인 ECC 절차 지침, (c) 언어·도구 중립적인 형식 예시뿐이다. 모델이 못 하는 일은 그 결과가 곧 측정값이다. 못 한다는 기록을 코드로 가리지 않는다.

## 6. 기존 템플릿 분기와 요청별 코드의 분리 방안

삭제는 사용자 결정이다. 아래는 **분리 대상 제안**이다. 근거는 감사 문서 §3·§4를 따른다.

| 대상 | 제안 | 비고 |
|---|---|---|
| 템플릿 ID 분기 8곳 이상(`runner/pipeline.py:341`, `runner/review.py:42`, `runner/sandbox.py:87`, `runner/release.py:72`, `backend/contracts.py:46-48`, `backend/config.py:25`, `backend/api.py:130,135`, `infra/checks/preview.py:47-49`) | 시작 프로젝트 ID를 데이터(`workspace.json`)로 읽고 코드의 이름 비교를 제거한다 | 정적 테스트로 `runner/`·`backend/`·`infra/`에 특정 템플릿 이름이 남지 않음을 강제(프론트 `task-neutral` 테스트와 같은 방식) |
| 요청별 구현 파일 | 실행 경로에서 분리해 "개발자 제공 참고 자료" 위치로 격리하는 안 | 삭제 여부는 사용자 결정. 서비스 단위 테스트의 가짜 모델 픽스처가 이를 쓰고 있어 대체 중립 픽스처가 먼저 필요 |
| 요청별 평가 스크립트 | `check_runner`로 대체 후 격리 | §2 |
| `backend/map_access.py` | 범용 "외부 접근 브로커"로 일반화하는 안: 공급자 허용표를 코드에서 빼고 **승인된 계획의 외부 접근 요청**에서 받는다 | 비공개 키 파일, 일일 한도, 429 중단, 응답 상한 같은 보호는 유지. 공급자 이름이 코드에 남지 않게 한다 |
| 공급자별 검색 어댑터 | 서비스 경로에서 분리 | 모델이 만들어야 할 앱 로직이다 |
| `Runtime.reasons`·`plan_support`의 요청별 문구 | 템플릿 이름이 아니라 **계획에서 계산한 지원 공백**(점검 없는 AC, 승인 범위 밖 의존성 등)만 서버가 만든다 | CR-C16(`template_id` enum)과 함께 결정(D6) |
| 계약 `template_id` enum | 시작 프로젝트 ID 패턴 문자열로 일반화하는 안과 서버 목록 검사의 동시 일반화 | 사무실 인계 CR-C16 초안과 동일 방향 |

## 7. 고정 조건 새 run 검증 절차 (3단계용 조건표 초안)

원칙: 조건을 **실행 전에** 고정하고 실행 중에는 손대지 않는다. 사용자 요청은 앱 입력 경로로 전달하고, 누가 전송했는지 기록한다. 기획·배포 결정은 사용자만 한다.

| 항목 | 고정 값 |
|---|---|
| 서비스 커밋 | 구현 후 확정할 해시(미정). 이 설계의 구현 커밋 이후로만 가능 |
| 추론 모델 | `qwen3.5:4b`(태그와 digest 기록), 추론 슬롯 1 |
| 임베딩 | `qwen3-embedding:0.6b`(digest 기록) |
| 도구 목록·정책 | §1.2의 도구 이름, `tool_policy_digest`, 허용 실행 파일 목록, 네트워크 정책 |
| 빈 시작 상태 | 시작 작업 공간 해시(앱 코드 없음), `workspace.json` 해시 |
| 입력 요청 | 사용자가 앱에 입력한 원문 그대로(변형·보강 금지) |
| 외부 접근 | 계획 승인에서 사용자가 허용한 범위만. 키는 비공개 파일, 채팅에 요구하지 않음 |
| 평가 기준(사전 등록) | 아래 |
| 개입 규칙 | 작업 공간·계획·점검·DB에 대한 개발자 직접 수정 없음. 서비스 결함을 발견하면 **그 run을 종료·보존**하고 수정 후 새 run으로 시작 |
| 중단 조건 | `needs_input`, 무진전 감지, 자원 부족, 사용자 중지. 실패는 지우지 않는다 |

평가 기준은 "앱이 완성됐는가"가 아니라 **모델이 무엇을 했고 어디서 막혔는가**를 기록하는 절차다.

1. 기획: 모델이 AC와 `check_spec`을 만들었는가. 점검 없는 AC는 몇 개인가.
2. 사용자 결정: 승인·수정·거절이 사용자 조작으로 기록됐는가(합성 승인 0건).
3. 구현: 모든 파일 변경이 도구 원장에 있는가. 원장 밖 변경이 있으면 개입 run이다.
4. TDD: RED(실패 기록) 뒤 GREEN(통과 기록)이 순서대로 있는가.
5. 독립 리뷰: validator·security 보고서가 각각 승인 점검 결과로 기계 판정됐는가. `not_run`·`error`는 통과로 세지 않는다.
6. 실패 분류: 모델 판단 실패 / 서비스 결함 / 환경 미준비를 근거와 함께 구분한다.
7. 결과 표기: 어느 단계까지 모델이 자율로 수행했는지 단계별로 쓴다. 중간에 사람이 넘겨받은 단계는 자율로 세지 않는다.

## 8. TDD 계획

모든 항목은 모델 없이 가짜 모델로 서비스 동작을 검증한다. 요청 내용에 기대지 않는다. 각 항목은 RED를 먼저 확인한다.

| 단계 | 테스트 |
|---|---|
| **F0 문맥 유형별 테스트** (설계 확정과 독립이라 먼저 가능) | 짧은 요청 1회 호출로 완료 / 긴 원문이 여러 조각으로 완료 / 여러 차례 정정에서 폐기된 요구가 되살아나지 않음 / 재기획에서 `prior_draft`가 전달되고 `approved_spec`은 승인본뿐 / 예산 초과 시 필수 조건을 자르지 않고 `needs_input`과 원문 보존 / 역할별 패킷에 다른 역할 보고서가 없음 / 동일 입력의 체크포인트 재사용 |
| F1 도구·격리 | 경로 이탈·심볼릭 링크·`.git`·크기 상한 거부 / 허용 밖 실행 파일 거부 / 셸 메타문자가 해석되지 않음 / 네트워크 none에서 외부 접근 실패 / 시간 초과·출력 상한 / 모든 호출이 원장에 남음 / 원장 불변 |
| F2 점검 명세 | 스키마 위반 거절 / AC 연결 점검 없음 → 승인 불가 / `check_runner`가 `expect`와 실제 결과를 대조해 판정 / 모델 보고서의 "통과" 문장은 판정에 영향 없음 / `not_run`·`error` ≠ 통과 / 승인 후 점검 변경은 재기획 필요 |
| F3 RED→GREEN | RED 기록 없이 impl 작업이 열리지 않음 / 처음부터 통과하는 테스트는 RED 불성립 기록 / 무진전 감지가 `needs_input`으로 이어짐 |
| F4 승인 결속 | `check_plan_digest`·`tool_policy_digest` 변경 시 이전 승인 무효 / 범위 밖 의존성·네트워크 요청이 자동 허용되지 않고 `needs_input` / 승인 합성 불가 |
| F5 분기 제거 | `runner/`·`backend/`·`infra/`에 특정 템플릿·공급자 이름이 없음을 정적 검사 / 시작 프로젝트 ID는 데이터에서만 읽음 / 중립 픽스처로 기존 서비스 테스트 이관 |
| F6 개입 감지 | 원장에 없는 작업 공간 변경이 있으면 run에 개입 표시 |

완료 기준은 기존 규칙(80% 커버리지, 독립 리뷰)을 따른다. 구현 순서는 F0 → F1 → F2 → F3 → F4 → F5 → F6이며, 각 단계 끝에서 관제에 보고한다.

## 10. 이 설계가 보장하지 않는 것

- 4B 모델이 완성된 앱을 만든다는 보장은 없다. 못 만드는 경우의 올바른 결과는 막힌 단계의 기록이다.
- 격리 환경 안에서 모델이 만든 코드가 안전하다는 보장은 없다. 독립 보안 검사와 사람의 배포 승인이 남는다.
- 선언형 점검 명세가 모든 종류의 요구(시각적 품질, 사용성)를 표현하지는 못한다. 그런 AC는 "사람 확인" 표시와 함께 사용자에게 남는다.
