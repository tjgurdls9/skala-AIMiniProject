이 절은 아래의 이전 기록보다 우선한다. 지시는 원본의 `docs/prompts/CLAUDE_PHASE_COMPLETION.md`와 `docs/planning/phase-completion.md`를 따른다. 기준은 Claude `b3a52bc`, Codex `c3e11c1`이다.

**사용자 디자인 지시 원문**
> 빈 화면에 텍스트 입력창 하나, 볼드한 타이포로 문구 하나
> 거기에 프롬프트 입력하면 화면이 팟 하고 전환되면서 화면 전체에 꽉 차게 사무실이 나와. 디자인 구성은 웹 서칭하고
> 스크롤을 아래로 내리면 꽉 찬 사무실이 크기가 줄어들면서 상세 작업 정보가 우측 패널과 사무실 애니메이션 아래에 표시되게

**구조화 요약**
1. 시작 화면: 빈 화면, 굵은 문구 하나와 입력창 하나.
2. 프롬프트 제출: 화면이 즉시 전환되며 사무실이 화면 전체를 채운다. 사무실의 시각 구성은 웹 조사로 정한다.
3. 아래로 스크롤: 사무실이 줄어들고, 상세 작업 정보가 우측 패널과 사무실 아래에 나타난다.

**기능 범위 영향**: API 변경은 없다. 기존 `ProjectCreate`(title, request)와 `RunCreate`(live)를 쓴다. 제목은 입력 원문의 첫 줄에서 만든다. 실제 기록 재생·합성 예시 진입, 실행 가능성 안내, 승인·중지·근거·접근성(DOM 대안·키보드·모션 감소)은 유지한다.
- P01–P03의 프론트 기능 연결을 커밋했다. P04/S08 본격 화면 개편은 이 세션 사용자의 직접 디자인 지시를 받은 뒤 시작한다.
- 이 대기는 개발용 인계이며, 제품 API의 기획·배포 승인 사건이 아니다. 기다린 시간이나 무응답은 지시나 동의가 아니다.

### S08 사용자 피드백 1 — 전환 저항

**원문**
> 다 좋은데 드래그로 전체창이랑 상세정보랑 왔다갔다할 때 조금 저항을 줘야할 것 같아. 어느정도 드래그값이 쌓여야 전환되도록? 지금은 잠깐 드래그를 해버리면 의도치 않게 화면이 바뀌어버려

**반영(`useSnapScroll`)**: 스크롤에 바로 따라가던 축소를 전체 화면과 상세의 두 상태 전환으로 바꿨다.
- 휠은 240px, 터치 드래그는 120px 이상 누적돼야 전환한다.
- 그보다 짧으면 진행도를 최대 0.08만 늘려 보여 주고, 입력이 220ms 멈추거나 손을 떼면 되돌아간다. 반대 방향 입력은 쌓인 값을 줄인다.
- 전환 직후 450ms는 관성 입력을 무시해 한 번에 두 번 바뀌지 않게 한다.
- 키보드나 스크롤바로 중간에 멈추면 140ms 뒤 가까운 상태로 맞춘다. "상세 작업 정보" 버튼은 바로 전환한다.
- 상세 아래쪽을 읽는 중의 휠은 막지 않는다. 모션 감소 설정이면 이동 애니메이션 없이 바로 옮긴다.

**확인**: 테스트 180개 통과(`tests/snap.test.ts` 12개 추가). 실제 Chrome에서 휠 사건을 보냈다: 짧은 휠 120px은 늘어남 0.06 뒤 0으로 복귀, 누적 300px은 상세로 전환, 직후 관성은 무시, 상세에서 짧은 위쪽 휠은 유지, 위쪽 누적 300px은 전체 화면으로 복귀. 실제 트랙패드와 터치 기기 손 조작은 사용자 확인이 필요하다.

### 관제탑 CT36·CT40 대응 (2026-10-21)

**CT36 — Claude 담당, `f5a26d5`에서 수정**
- 지적: 같은 명세에서 수정 Sprint·재검토로 보고서가 비거나, AC 조회가 지연·실패해도 옛 "충족"이 남을 수 있었다. 근거 보고서가 사라진 met도 충족으로 보였다. 근거 패널에는 AC 오류 안내가 없었다.
- 수정:
  - 판정을 조회 시작 시점의 스냅샷 `state_version`에 묶었다. 현재 스냅샷과 버전·명세가 모두 같을 때만 표시하고, 다르면 "판정 갱신 중"으로 둔다.
  - 조회가 실패하면 이전 판정을 지우고 오류만 남긴다.
  - 근거 보고서 ID가 현재 `reports`에 없거나, met인데 근거가 없으면 "근거 없음(무효)"으로 표시하고 충족 수에 넣지 않는다.
  - 근거 패널에도 Sprint 영역과 같은 AC 안내를 전달한다.
- 근거: `tests/ct36.test.ts` 6개. (1) 같은 명세에서 reports=[]로 버전만 오른 상태에서 새 판정 전 옛 met를 숨기고, 늦게 온 옛 met는 무효 처리. (2) 옛 버전의 조회가 늦게 끝나도 현재 버전 판정으로 쓰지 않음. (3) 조회 실패 시 판정 삭제. (4) 근거 없는 met 무효 집계. (5) 목록 표시. (6) 근거 패널 안내. 이전 `useRun.ts`로 되돌리면 (1)~(3)이 실패하고, 수정 후 전체 188개가 통과한다.
- 남은 것: 실제 LIVE 서버에서 스타일 수정·재검토를 거치는 흐름의 화면 확인은 하지 않았다(합성 스냅샷과 가짜 출처로만 재현). Codex 통합본(`c4941bb`, `0dbe45e` 기준)에는 이 수정이 아직 없다. 통합 전에는 CT36을 해소로 보지 않는다.

### M3 정정 — 관제탑 지적 반영

- **무엇이 틀렸나**: `ef1dd16`에서 M3를 고쳤다고 보고했다. 그러나 `useRun.ts`의 `applySnapshot`에는 "스냅샷 `state_version`이 명령 시점보다 크면 확인 표시를 지운다"는 조건이 남아 있었다. 다른 작업으로 버전이 올라가도 내 명령이 반영된 것처럼 보였다. 테스트도 같은 명령 사건과 시간 초과만 다뤘다. 보고가 코드보다 앞서 나갔다.
- **확인한 서버 동작**: Codex `a70a7b1`의 `backend/store.py` `command()`를 읽기 전용으로 확인했다. 서버는 명령을 받으면 같은 트랜잭션에서 상태를 바꾸고, `command_id`가 담긴 사건(`run_state_changed`, `approval_decided`, `changes_requested`)을 저장한 뒤 202를 돌려준다. 그래서 같은 명령 ID 사건을 반영 근거로 쓸 수 있다.
- **고친 내용**: 버전 기반 해제 조건을 삭제했다. 확인 표시는 같은 `command_id` 사건이 오거나 시간이 초과할 때만 풀린다.
- **테스트**
  - 버전 증가로 해제를 기대하던 기존 테스트를 바로잡았다.
  - "다른 작업으로 `state_version`이 올라도 확인 표시가 유지된다"와 "다른 `command_id` 사건으로는 풀리지 않는다"를 추가했다.
  - 이전 조건을 잠시 되돌리면 새 테스트가 실패하고, 수정 후에는 통과한다. 전체 120개 통과.
- **남는 의존**: 확인은 서버가 명령 반영 사건에 `command_id`를 넣는 현재 동작에 기대고 있다. 계약 §7에 이 보장이 명시되어 있지 않아 CR-C11로 요청한다.

보류: L2(누락 재동기화의 백오프·최대 횟수), L3(사건 추가 O(n²)). 긴 실행이나 비정상 서버에서만 드러나므로 실제 LIVE 사건 규모를 본 뒤 처리한다.

## 계약 요청 (새 요청)

**CR-C09 AC 충족 상태**
- 동작: Sprint와 전체 AC 충족 현황을 작업 진행과 구분해 보여준다.
- 부족: Snapshot·PlanView 어디에도 AC별 판정이 없다. 현재 화면은 "충족 판정은 서버가 아직 제공하지 않음"이라고 표시한다.
- 제안: 판정 주체(검증 보고서)에 묶인 `acceptance: [{id, status: "unmet"|"met"|"failed"|"not_run", report_id?}]`
- 호환성: Snapshot 확장이라 protocol 버전 검토가 필요하다. 또는 별도 GET으로 받는다.
- 그동안: 정의 개수만 표시한다.

**CR-C10 preview 아티팩트 본문 형식 확인**
- 동작: 프리뷰 dialog가 `GET /api/artifacts/{preview id}`를 `http.Preview`로 해석한다.
- 부족: 계약 §7은 spec만 PlanView로 명시한다. preview 종류가 `http.Preview`를 반환하는지 명시가 없다.
- 제안: "kind: preview → http.Preview" 한 줄을 명시한다.
- 그동안: 형식이 다르면 "프리뷰 주소 없음"으로 표시하고 열지 않는다.

**CR-C11 명령 반영 사건의 `command_id` 보장**
- 동작: 명령 접수(202) 뒤 "반영 확인 중"을 정확히 끝낸다.
- 부족: 현재 서버는 명령으로 상태를 바꾼 사건에 `command_id`를 넣지만, 계약에는 명시가 없다. `state_version`은 다른 작업도 올리므로 반영 근거가 되지 못한다.
- 제안: "접수된 명령이 만든 공개 사건에는 그 `command_id`를 포함한다"를 계약 §4 또는 §7에 명시한다.
- 호환성: 현재 구현과 같으며, 문서 명시만 필요하다.
- 그동안: 같은 ID 사건이 없으면 20초 뒤 "반영 미확인"으로 조작을 풀어 준다.
