# 로컬 모델 비교: qwen3.5:4b 기준선 대 7B급 코딩 모델 2종 (개발 확인 · 수용 아님)

2026-10-21. 사용자가 (나) "16GB에서 도는 다른 무료 로컬 모델 비교"를 골랐다. 운영 기본 모델은 바꾸지 않았다. 변경 결정은 이 결과를 보고 사용자가 한다. 외부·유료 모델 호출은 없다. 표본은 모델·작업당 1회(temperature 0)라 통계적 결론이 아니다.

## 조건

3차 C와 같다: 같은 두 작업(Python 덧셈 함수, 문자열 뒤집기 함수), 작업당 40회 또는 20분, 정답·힌트 없음, 같은 프롬프트·동작 스키마·서버 게이트, `think=False`, `num_ctx` 16384, 추론 슬롯 1(`OLLAMA_NUM_PARALLEL=1`, `OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_NO_CLOUD=1`). 한 번에 한 모델·한 작업, 모델 전환 전 언로드 확인, 메모리 감시자(여유 15% 미만 또는 스왑 4GB 초과 2회 연속이면 중단)를 켠 채 실행했다. 기준 상태: 재부팅 후 스왑 0, 시스템 여유 54–61%, Docker VM 메모리는 측정 시점마다 다르게 보고됐다(8.3GB, 7.8GB, 6.2GB; 설정은 바꾸지 않았다).

## 막힌 지점

- **qwen2.5-coder:7b**: 세 번 모두 같은 동작을 냈다. 테스트 없이 구현 파일(`add.py`, `reverse.py`)을 먼저 쓰려 했고, 서버가 "테스트 파일 기록 없음. RED 판정에는 …" 사유로 거부했는데도 같은 호출을 반복했다(관찰 사유를 반영하지 않음). 형식은 100% 맞았다. 기준선 4b는 테스트를 먼저 쓰고 RED에 도달했으므로 이 표본에서 7B가 TDD 순서 면에서 더 나빴다.
- **deepseek-coder:6.7b**: 모델이 올라간 직후 상주 메모리가 **12,050MB**에 이르렀고(가중치 3.8GB + 전체 어텐션의 KV 캐시, `num_ctx` 16384에서 약 8GB로 추정, 미검증) 여유 메모리 4%, 스왑 4,184MB에서 감시자가 발동했다. 감시자가 이 실행이 띄운 `ollama serve`와 `lifecycle-` 컨테이너만 종료했고 남은 프로세스·컨테이너는 없었다. 이 컨텍스트 설정으로는 16GB에서 쓸 수 없다. 더 작은 컨텍스트에서의 동작은 측정하지 않았다.

## 판단과 한계

- 이 표본에서 qwen2.5-coder:7b는 기준선 4b보다 낫지 않았다(형식은 같고 TDD 순서를 지키지 못함, 메모리는 약 1.5배). deepseek-coder:6.7b는 이 장비·설정에서 쓸 수 없다. 모델 크기가 병목이 아니라 "관찰 사유를 반영해 다음 동작을 고르는 능력"이 병목으로 보인다.
- 깨끗한 기준 상태에서 7.6B 모델(상주 약 5.3GB)과 컨테이너 1개는 16GB에서 여유 34%로 함께 돌았다. 다만 이것은 컨테이너 1개와 다른 앱이 정리된 상태의 측정이며, 다른 역할 세션과 앱이 함께 도는 환경(앞선 사건에서는 스왑이 13.8GB였다, [사건 기록](memory-incident-20261021.md))에서의 안전성은 측정하지 못했다. 그 환경에서는 7B급을 운용할 수 없었다는 사실이 이미 있다.
- 한계: 모델·작업당 1회, 작업 두 개, 프롬프트는 4b에 맞춰 다듬어진 상태(7B에 맞춰 조정하지 않음), `concurrent_load` 테스트는 구현과 함께 작성해 별도 RED 실행이 없다.
- 운영 모델은 바꾸지 않았고, 바꾸는 결정은 사용자가 한다.
