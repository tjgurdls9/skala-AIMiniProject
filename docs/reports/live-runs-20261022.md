## 결함 수정이 run을 어떻게 진전시켰는지

1. **work_plan 영역 판정(수정 A, `7af3434`)**: 처음 4개 live run(67f60a, d90ff1, e1626c의 첫 기획 등)은 모두 모델이 `ai_data`를 작업에도 생략 이유에도 넣지 않아 멈췄다. temperature 0이라 같은 입력은 같은 출력으로 재현됐다. 영역 판정을 `{needed, reason}` 고정 키 4개의 응답 스키마로 강제하자(서비스는 아무것도 채우지 않는다) 5d13ca에서 모델이 `ai_data`를 `needed=false`와 스스로 쓴 이유로 판정해 **work_plan을 통과**했다.
2. **모델 원문 기록(수정 B, `7af3434`)**: 앞의 두 번의 실패는 모델이 무엇을 냈는지 알 수 없어 분석이 막혔다. 내부 원장 `model_outputs`가 생긴 뒤부터 5d13ca·ce7a5d의 응답과 서버 거절 사유를 확인할 수 있었다.
3. **샘플링 스키마의 역슬래시 패턴(`5244633`)**: 5d13ca가 verification에서 Ollama 400으로 멈춘 것은 모델이 아니라 서비스 결함이었다. http 점검 `path` 패턴 `^/[^\s]{0,200}$`를 Ollama가 문법으로 컴파일하지 못했다. 역슬래시가 든 패턴을 샘플링용 스키마에서 빼고(서버는 원 스키마로 다시 검증한다) Ollama 400을 "서비스 설정 또는 스키마 오류"로 분류하게 했다. 실제 `qwen3.5:4b`로 verification 스키마 호출이 통과함을 직접 확인했다. 그 결과 ce7a5d가 **verification에 도달**했다. 이 단계는 이전에 한 번도 실모델로 실행된 적이 없었다.
4. **정정 조각의 오류 피드백(`a7dc5af`)**: e1626c의 재기획은 검사 실패 즉시 멈췄다. 이제 거절 사유를 모델에 돌려주고 같은 오류가 두 번 나올 때만 멈춘다. 철회·대체 근거 규칙은 약화하지 않았다. 이 수정은 단위 테스트로만 확인했고 실서버 run에서는 아직 확인하지 못했다.

5. **오류 사유의 정확도(`876be45`)**: ce7a5d의 모호한 사유("c3 …")를 모델이 쓴 실제 점검 id와 "작업 공간 기준 상대 경로" 안내로 바꿨다. b7630a·3e1730에서 사유는 정확해졌지만 4B는 같은 절대경로를 반복했다.
6. **주기 2 반복 감지(`33fe0e7`)**: b7630a에서 모델이 두 가지 틀린 답을 번갈아 내자 "같은 오류가 연속 두 번"이라는 멈춤 규칙이 걸리지 않아 추론을 45회 넘게 소비했다. 이미 본 오류가 (다른 오류를 사이에 두고라도) 돌아오면 멈추도록 고쳤고(횟수 상한은 없음), 3e1730은 5번 응답 만에 사용자 입력 요청으로 끝났다.

7. **정책을 샘플링 스키마로 강제(`dd7d496`)**: 3e1730에서 4B는 `curl` 점검과 절대경로 file 점검을 반복했다. 사유가 정확해도 같은 답을 냈으므로, command 점검의 `argv[0]`은 TOOL_POLICY가 허용하는 인라인 실행 파일(python, python3, node)로, file 점검의 `path`는 `/`로 시작할 수 없게 응답 형식 자체에 넣었다(서버는 원 계약 스키마로 다시 검증). 실제 모델로 먼저 확인했고 결과: fa83e2가 **verification을 통과하고 처음으로 기획 승인 단계에 도달**했다.
8. **쓰기 범위의 상대 경로(`e270814`)**: fa83e2가 빌더에서 멈춘 이유(모든 쓰기가 범위 밖으로 거절됨)를 고쳤다. work_plan의 `write_scope`도 `/`로 시작할 수 없게 샘플링 스키마로 강제하고, 서버 검사가 절대경로·`..`·`.git` 범위를 "작업 공간 기준 상대 경로 glob" 사유로 거절한다. 이 수정은 fa83e2에는 적용되지 않았다(이미 승인된 기획은 바꿀 수 없다).

## ce7a5d 진단(모델이 낸 응답 요약)

- 모델은 `file` 점검의 `path`를 절대경로 `/app/routes/tasks.py`로 냈다. 서버는 작업 공간 기준 상대 경로만 허용하므로 거절했고 사유를 돌려줬지만 모델이 **같은 절대경로를 다시 냈다**(응답 2번 모두 동일).
- 서비스 쪽 원인: 거절 사유가 모델이 낸 점검 id(`CHK-003`)가 아니라 서버 내부 임시 id `c3`를 가리켰고, "작업 공간을 벗어나거나…"는 상대 경로로 쓰라는 말을 하지 않아 모델이 무엇을 고칠지 알기 어려웠다. 모델 쪽 원인: 절대경로 사용과 같은 실수 반복.
- 판정: **복합 원인**(모델 절대경로 + 서비스 피드백 문구). 모델이 가정한 존재하지 않는 import 구조(`from routes.tasks import create_task` 등, 아직 만들지 않은 코드를 전제)는 모델 품질의 한계로 기록한다.
- 서비스 쪽 수정(점검 오류에 모델의 실제 id를 쓰고 file 경로는 상대 경로라고 안내, `876be45`)은 이 run에는 적용되지 않았고 b7630a·3e1730에 적용됐다.
